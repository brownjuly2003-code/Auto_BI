# Unlisted paths: what the filesystem refuses to list or to look at is not what is not there — проверки автора

**Дата:** 2026-10-05
**Срез:** T-52; verifier 92 → 93 / check 67 → 68
**Автор:** Claude Opus 5.5 (`claude-opus-5-5`), напрямую, без MyFlow-исполнителей
**Модельное ревью:** не проводилось

Владелец в этой сессии выбрал прямое исполнение: спеку, код, тесты и доки написал Claude
Opus 5.5, MyFlow не запускался, synthetic Astra xhigh review не было. По
[ADR 0006](../adr/0006-modelled-review-development-gate.md) модельное ревью не выполнено, пока
нет фактического результата Astra xhigh, — у этого среза его нет. Всё перечисленное ниже —
проверки автора над собственной работой: не независимое ревью, не human/design-partner
acceptance и не production acceptance. Тесты и пробы прогонялись на Mac (Python 3.13.13,
3.12.13 и 3.14.6). Контракт: [files a command cannot read](../specs/unreadable-inputs.md),
четвёртое требование.

Предыдущий срез оставил две границы: путь, на который команде нельзя посмотреть, вне semantic
ref и файлов под assets кончал её traceback; каталог, который нельзя перечислить, читался
как пустой. Обе — ответы `pathlib`, которые теряют отказ файловой системы:

- `Path.rglob` читает каталог, который не может перечислить, как пустой: `OSError` скана
  гасится там же, где брошен. Измерено на Python 3.12.13, 3.13.13 и 3.14.6.
- `Path.exists`, `Path.is_file` и `Path.is_dir` с Python 3.14 отвечают `False` на любой
  `OSError`; до 3.13 взгляд на путь под каталогом, в который нельзя войти, бросал
  `PermissionError`. Проект объявляет `requires-python >= 3.12`, так что 3.14 — поддерживаемый
  интерпретатор, и на нём то, что предыдущий срез сделал usage error, молча стало «файла нет».

На HEAD `35c18ec` воспроизведено настоящим CLI как процессом на macOS: прогон, который
проходит, и один каталог без части прав. Режим 000 — каталог нельзя ни перечислить, ни войти
в него; 0o300 — войти можно, перечислить нельзя (файл в нём открывается по имени); 0o400 —
перечислить можно, войти нельзя (имена видны, посмотреть ни на что нельзя). 32 прогона
`decision verify`, 15 `decision capture` и 8 `decision validate` на каждом из двух
интерпретаторов:

Что стоит за числами HEAD:

- Каталог assets или каталог под ним, в котором лежит asset продукта, с режимом 000 или 0o300:
  `decision verify` выходит с 0 и `pass_with_advisory` — asset не выбран, и ничто не говорит,
  что его не удалось выбрать (4 прогона). Вторая копия asset в таком каталоге тоже не видна,
  хотя два assets одного id — usage error. `decision capture` отвечает `no verified asset under
  <путь>`.
- Каталог metrics base ref — exit 3, candidate ref — exit 4, оба на snapshot без метрик.
  `decision capture` с таким каталогом candidate идёт открывать запрос к движку.
- Validated-каталог — exit 2 `no decision product contract found in the given paths` у обеих
  команд. Каталог под ним с контрактом метрики — продукт блокируется `metric_ref.unknown`,
  будто контракта никто не писал; с продуктом — тот же exit 2; пустой — exit 0. Каталог не
  назван нигде.
- Путь под каталогом, в который нельзя войти, — путь assets, каталог dashboards, dashboard
  spec, recorded results, validated-файл, output capture: на 3.13 — 9 traceback (6, 2 и 1). На
  3.14 те же пути «не найдены» (`verified assets path not found`, `dashboard specs directory not
  found`, `recorded results file not found` — о путях, которые на месте), spec становится
  finding `bi.spec_missing` с exit 3, validated-файлы дают `no decision product contract found`,
  а `decision capture` открывает запрос, не посмотрев на output.
- На 3.14 каталог с режимом 0o400 тоже читается как пустой: взгляд на каждый файл, который
  назвало перечисление, отвечает `False`, и файл пропускается. С каталогом assets `decision
  verify` выходит с 0 и `pass_with_advisory`, с каталогом metrics — с 3 (base) и 4 (candidate)
  — там, где 3.13 отвечал `cannot read <файл>: PermissionError`.

Теперь взгляд и обход спрашивают операционную систему сами (`auto_bi/filesystem.py`: `os.stat`
и `os.scandir`). «Нет» — только то, чем система отвечает о пути, которого нет: `ENOENT`,
`ENOTDIR`, `EBADF`, `ELOOP`, на Windows ещё коды 21, 123 и 1921, и имя с NUL. Это тот же
набор, который `pathlib` до 3.13 читал как «нет»; любой другой отказ остаётся отказом. Обход
даёт те же пути, что `rglob("*")`, когда каждый каталог перечисляется: ссылку на каталог даёт
и не идёт по ней. Каталог, который не перечисляется, — отказ с именем этого каталога; каталог,
который перечислен, но файловая система не говорит, какие из его записей каталоги, — такой же
отказ, один на каталог.

Что из этого следует для команд:

- Validated paths. Отчёт валидации отвечает за каждый файл под своими путями, поэтому каталог,
  который не перечислен, — отдельный issue: `contract.unreadable`, block, путь каталога в
  subject и source, `cannot list directory: <класс>`. Путь, на который нельзя посмотреть, —
  `cannot look at path: <класс>`; путь, которого нет, — `path does not exist`, как прежде. Всё,
  что перечислилось, загружается и валидируется. Гейт грейдит такой issue как любой
  `contract.unreadable`: `contracts.validate` — block, exit 4, bundle записан.
- Нет продукта. Когда среди прочитанного нет продукта, `decision verify` называет
  непрочитанное: `no decision product contract found in the given paths; <n> path(s) could not
  be read: <путь> (<сообщение>), …` — первые три issue `contract.unreadable`, затем
  ` (+<k> more)`. Так же продолжается `no decision product '<id>' in the given paths (…)`.
  Без таких issue обе строки прежние. `decision validate` печатает отчёт над своей ошибкой и
  называет их там.
- Semantic ref, путь assets, входы прогона. Каталог, который не перечисляется, и путь, на
  который нельзя посмотреть, кончают `decision verify` и `decision capture` usage error
  предыдущего среза: `error: cannot read <путь>: <класс>`, exit 2, одна строка, до грейда,
  вопросов движку и записи. Output capture, на который нельзя посмотреть, — `cannot write
  captured result <output>: …` до вопроса движку.

Версии evidence: `VERIFIER_VERSION` 92 → 93, `CHECK_VERSION` 67 → 68. Прогон над validated
paths с каталогом, который не перечисляется, и на HEAD давал bundle: с пустым таким каталогом
— `pass_with_advisory`, с контрактом метрики в нём — block с одним `metric_ref.unknown`. Теперь
отчёт валидации в bundle другой и вердикт первого — block. Исторические bundles не
переписаны.

Выбор. Обе границы назвал предыдущий срез; срез выбрал оркестратор, Astra-выбора по ADR 0006
для него нет. Решения внутри среза — тоже автора:

- Finding под validated paths и usage error в ref и под assets — та же асимметрия, что у
  файла, который не открывается: отчёт валидации отвечает за свои пути, будет за ним прогон
  или нет, а snapshot говорит, с каких байтов он снят, и у каталога, который никто не
  перечислил, байтов нет.
- Каталог, который не перечисляется, останавливает отчёт или прогон, что бы в нём ни лежало:
  команда не может знать, что контрактов и assets в нём нет. Проба: пустой такой каталог под
  validated paths на HEAD давал exit 0, теперь — exit 4.
- Один модуль вместо правки каждого места: взгляд через `pathlib` на 3.13 и на 3.14 отвечает
  по-разному, и отличить место, где это важно, от места, где нет, можно только прогоном на
  обоих. `decision evidence` и store на него не переведены — отдельный срез, см. границы.
- Набор «пути нет» взят у `pathlib` до 3.13, а не сужен до `ENOENT`: тогда ответы на всё, что
  не отказ, остаются прежними на 3.12 и 3.13.
- Обход не идёт по ссылке на каталог — как `rglob("*")`; дифференциальный тест сверяет обход с
  `rglob` на дереве со ссылками.
- Отказы одного validated-пути сортируются по путям каталогов: порядок обхода — порядок
  файловой системы, и отчёт от него зависеть не должен.
- `decision verify` без продукта называет не больше трёх путей: строка usage error — одна.
- Сообщение output capture — прежнее сообщение отказа записи, с текстом отказа как есть.

Границы. Срез закрывает `decision validate`, `decision verify` и `decision capture`. `decision
evidence` и filesystem store по-прежнему смотрят через `pathlib`: проба — 7 прогонов над
записанным bundle с каталогом evidence, каталогом прогона или каталогом над ними без части
прав — даёт на обоих деревьях 6 traceback на 3.13.13 и 3 на 3.14.6, где ещё три отвечают `no
evidence bundle under <путь>: no run directory holds manifest.json` или `evidence path not
found: <путь>` о bundle, который на месте; в седьмом каталог bundle, который не читается,
назван `evidence.artifact_missing` — «is not in the store». Отказ отличается от «пути нет» по
ответу операционной системы; ответы Windows и каталог, чьи записи не различаются, подставлены
тестами — на Windows и на файловой системе, которая не сообщает вид записи, ничего не
запускалось. Настоящие права проверены на macOS под пользователем, которого права
останавливают; процесс, которого они не останавливают (root), отказа не получает, и тесты с
правами там пропускаются. Каталог, который не перечисляется, останавливает отчёт и прогон,
даже если он пуст: validated-путь с таким каталогом блокируется, пока каталог не станет
читаемым или не уйдёт из путей. Под validated-путём файл выбирается по имени, как прежде:
каталог с именем `*.yaml` — контракт, который не читается (`cannot read contract:
IsADirectoryError`, проверено пробой); в ref и под assets такой каталог пропускается, как
прежде. Порядок обхода — порядок файловой системы; каждый читатель сортирует прочитанное сам.
Каталог dashboards не перечисляется никогда. Output capture под каталогом без права записи
по-прежнему обнаруживается после запроса к движку. Запись manifest не атомарна; входы
`decision investigate` и загрузчики v1-раннтайма не тронуты. BI и DWH не запускались: проверка
offline. Независимого ревью у среза нет — ни модельного, ни человеческого.
