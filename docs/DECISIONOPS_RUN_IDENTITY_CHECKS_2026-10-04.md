# Run identity: idempotency key covers every static gate input — проверки автора

**Дата:** 2026-10-04
**Срез:** T-47; verifier 91 / check 66
**Автор:** Claude Opus 5.5 (`claude-opus-5-5`), напрямую, без MyFlow-исполнителей
**Модельное ревью:** не проводилось

Владелец в этой сессии выбрал прямое исполнение: спеку, код, тесты и доки написал Claude
Opus 5.5, MyFlow не запускался, synthetic Astra xhigh review не было. По
[ADR 0006](adr/0006-modelled-review-development-gate.md) модельное ревью не выполнено, пока
нет фактического результата Astra xhigh, — у этого среза его нет. Всё перечисленное ниже —
проверки автора над собственной работой: не независимое ревью, не human/design-partner
acceptance, не измерение времени человека и не production acceptance. Тесты и пробы
прогонялись на Mac (Python 3.13.13, pydantic 2.13.4); на Windows запускалась одна проба
кросс-платформенного сравнения. Контракт: [run identity](specs/run-identity.md).

`run_id` — функция idempotency key (ARCHITECTURE §7.6): повтор может переиспользовать только
bundle с тем же ключом, и другой bundle под запечатанным `run_id` отклоняется. До этого среза
ключ строился из digest продукта, canonical digests двух snapshots, policy, environment ref,
signing identity и версии verifier. Гейт получает больше, и всё остальное доходит до evidence:
validation report и validated-контракты грейдит `contracts.validate`, verified assets —
`assets.invalidated`, `results.reconcile` и `results.provenance`, dashboard specs и candidate
model — `impact.products` и `bi.contract`, gaps — `semantic.gaps`, а оба snapshot запечатаны
целиком вместе с digest прочитанных байтов. Границу «validated contract set вне idempotency
key» записали спеки T-45 и T-46. На HEAD `0aa44a8` через `decision verify` воспроизведено —
два прогона, различающиеся ровно одним входом:

- validated-контракт запинненной метрики `active` против `draft`: один `run_id`, вердикты
  `pass_with_advisory` и `block`;
- другие expected rows verified asset: один `run_id`, `results.reconcile` — pass с
  `result.equivalent` и block с `result.not_equivalent`;
- measure дашборда на колонку, которой модель не объявляет: один `run_id`, `bi.contract` —
  pass и block с `bi.spec_invalid`;
- непрочитанный контракт рядом с контрактами candidate ref (canonical digest тот же): один
  `run_id`, `semantic.gaps` — pass и block, шесть проверок `check.not_run`;
- комментарий в candidate или base `model.yaml`: один `run_id`, другой артефакт snapshot;
- входы гейта с validated-контрактами и без них: один `run_id`, `contracts.validate` —
  review и pass;
- CLI: прогон с validated draft — exit 4; повтор в тот же каталог evidence после возврата
  контракта в `active` — exit 2, `refusing to overwrite it with … (same idempotency key,
  different evidence)`, в каталоге остаётся один bundle с вердиктом `block`.

`run_id` не говорил, какая это верификация, а исправленный вход нельзя было перепроверить
в том же каталоге evidence: отказ объяснял себя наблюдением другого момента.

Теперь ключ несёт ещё одну часть — `inputs`: content address каждого статического входа,
который гейт получает целиком. Это validation report, validated-контракты по id метрики, base
и candidate snapshot (граф, gaps, digest и описание источника, capabilities), candidate
model, dashboard specs по ref и verified assets. Прежние семь частей ключа не тронуты. Два
прогона, различающиеся любым таким входом, получают разные ключи и `run_id`, дошло отличие до
проверки или нет; порядок передачи контрактов, specs и assets ключ не двигает. Наблюдения
момента — записанные результаты кандидата, показания движка, `created_at` — остаются вне
ключа, как решил §7.6: повтор с другими наблюдениями делит `run_id` и в одном каталоге
отклоняется. Ни одна проверка, finding, вердикт или артефакт не меняются иначе, чем через
`run_id`, который несут. `VERIFIER_VERSION` 90 → 91: те же входы дают другой `run_id`, и
bundle verifier 90 не переиспользуется под сегодняшним ключом. `CHECK_VERSION` остаётся 66:
ни одна проверка не грейдится другим правилом. Исторические bundles не переписаны.

Выбор. Срез закрывает границу, записанную в спеках и проверках T-45 и T-46; его выбрал
оркестратор, Astra-выбора по ADR 0006 для него нет. Решения внутри среза — тоже автора:

- Вход покрыт целиком, а не той частью, которую читает проверка. Snapshot и так запечатан
  целиком, а «часть, которую читает проверка» менялась бы с каждой новой проверкой. Цена
  записана в границах: вход, не меняющий ни одного finding, — другой прогон.
- Решение §7.6 о наблюдениях момента не пересматривалось.
- Content address входа — digest точного текста, который пишется только для ключа, а не
  RFC 8785. Каноническая форма evidence отказывает float, целому за пределом ±(2^53−1) и
  одиночному суррогату; её вариант для чужих payload'ов пишет два целых за этим пределом
  одним double и отказывает non-finite. Гейт на HEAD завершает прогоны с такими значениями
  (невалидный dashboard spec с фильтром `.nan` — `bi.spec_invalid`; статистика витрины
  10^400; одиночный суррогат в synonym модели или в description validated-контракта),
  поэтому ключ на их канонизации добавил бы прогону точку отказа либо слил бы разные входы.
  В тексте объект пишется по отсортированным ключам, целое и float — в шестнадцатеричной
  записи, строка — ASCII-литералом.
- Строка как ASCII-литерал — исправление, найденное собственной проверкой автора до
  коммита. Первая реализация писала строку как ASCII JSON; JSON записывает символ вне BMP
  парой суррогатов, а строка может держать эту пару и сама (YAML читает `"\ud83d\ude00"` как
  два code points). Воспроизведено на первой реализации: символ U+1F600 и такая пара давали
  один текст. Литерал читается обратно в ту же последовательность code points.

Проверки автора — на рабочем дереве среза, на Mac, если не сказано иное:

- Спека написана до кода: пять требований, 25 сценариев. Факты о HEAD сняты пробами до
  реализации. После реализации в спеку добавлены сценарий о символе вне BMP, сценарий об
  обратном чтении строки и сценарий о порядке дампа (затем дополнен `type`-алиасами);
  сценарий «an input that changes no finding» приведён к тому, что проверяет тест.
- Новый модуль `tests/test_run_identity.py` — 91 тест: по тесту на каждый сценарий спеки,
  таблица двенадцати изменённых входов, раскладка полей `GateInputs` на статические и
  наблюдения с проверкой, что других полей нет, snapshot целиком (gaps, digest и revision
  источника, capabilities с обеих сторон), повторы в один каталог evidence, значения,
  которым каноническая форма отказывает. Против `auto_bi` из HEAD `0aa44a8`: 74 failed /
  17 passed. Прошедшие — контроли, от нового ключа не зависящие: набор полей `GateInputs`,
  поля `product` и `environment_ref`, два наблюдения, другие записанные результаты, два
  отказа в одном store, равные входы, восемь тестов порядка дампа. На рабочем дереве —
  91 passed.
- Отрицательный контроль теста порядка дампа: модель с полями `set`, `bytes`, `Any`, mapping
  с нетекстовым ключом и `frozenset` за `type`-алиасом — тест называет все пять полей и не
  называет mapping, ключ которого объявлен алиасом текста. Раскрытие `type`-алиасов —
  исправление теста, найденное собственной проверкой автора до коммита: первая версия
  обходчика останавливалась на алиасе и не доходила до aggregate checks в tolerance verified
  asset (`type AggregateCheck = …`), то есть утверждала больше, чем проверяла. Отдельный
  тест теперь требует, чтобы поля этих проверок были среди перечисленных.
- Форма дампа, проба по 48 моделям, достижимым из шести моделей статических входов: во всех
  `extra="forbid"`, ни приватных атрибутов, ни alias, ни исключённых из дампа полей, ни
  собственных сериализаторов, ни computed fields; единственный union моделей — aggregate
  checks, его члены различает `kind`. Единственное float-поле — значение фильтра дашборда;
  JSON-дамп pydantic 2.13.4 оставляет `nan`, `inf`, `-inf` и `-0.0` числами с плавающей
  точкой, и точный текст у каждого свой.
- CLI в одном каталоге evidence: validated draft — exit 4; после исправления — exit 0,
  `pass_with_advisory` под другим `run_id`; в каталоге два bundle, `decision evidence --run`
  по каждому — pass, 0 problems. Те же входы с тем же `--created-at` — тот же `run_id` и
  evidence digest, один bundle. Другие записанные результаты и повтор без `--created-at`
  (время берётся с часов) — exit 2, как на HEAD.
- Контроль на tracked pilot-пакетах: пять пакетов, 9 продуктов и chart-impact overlay —
  10 прогонов. Вердикт и каждая проверка (status, summary code) совпадают с HEAD во всех
  10; ни один `run_id` не совпадает с HEAD. Три повтора каждого прогона — два каталога и
  повтор в первый — дают один `run_id`, один evidence digest и один bundle в каталоге.
  Различных `run_id` 6 против 5 на HEAD: overlay, который меняет только dashboard spec,
  получил собственный. Прогоны, различающиеся только `results.yaml` (`ch-control` и
  `ch-result-drift`), по-прежнему делят `run_id`; пакеты `ch-tz-margin` и `ch-tz-revenue`
  побайтово равны вне каталогов evidence и делят его же.
- Детерминизм между процессами и машинами: те же 10 прогонов под `PYTHONHASHSEED=1` и `2`
  дают те же `run_id` и evidence digests; на Windows (Python 3.13.7) — те же `run_id`,
  evidence digests, вердикты и проверки, что на Mac.
- Значения, которым отказывает каноническая форма, на HEAD и на рабочем дереве: исходы
  совпадают по каждому из 12 случаев. Завершаются оба раза невалидный spec с `.nan` и с
  10^400, валидный spec с float и с 2^60 в фильтре, статистика 10^400 и 2^70, суррогат в
  synonym и в description; на HEAD у всех один `run_id`, на рабочем дереве — у каждого свой.
  Оба раза останавливают прогон в `bi.contract` валидный spec с `.nan`, `.inf`, 10^400 в
  фильтре и суррогатом в title; verified asset с суррогатом отклоняется как невалидный.
- Стоимость: на pilot-пакетах ключ выводится не дольше 1,75 мс — до 2,2% прогона (на HEAD
  0,27 мс). Рост линейный: candidate model из 1000 таблиц и 6000 колонок — 111 мс,
  из 5000 таблиц и 30000 колонок — 653 мс. Глубина рекурсии ограничена схемой: ни одна
  модель входа не рекурсивна, вложенность значения фильтра не глубже списка.
- Изменённые существующие тесты: сценарий «gate inputs without validated contracts» в
  `tests/test_product_metric_pin_rules.py` и его пара в
  `tests/test_product_metric_pin_contents.py` ждут разные `run_id` (прежде — один); тест
  версий переехал в новый модуль. Остальные существующие тесты не менялись, включая
  `test_the_same_environment_does_not_move_the_run_id` и
  `test_the_same_inputs_produce_the_same_run_and_the_same_bundle`.
- Спека [product metric pins](specs/product-metric-pins.md): сценарий о входах без
  validated-контрактов и граница об idempotency key приведены к новому правилу.
- Ruff, Black и strict mypy (120 модулей) чистые; концы строк изменённых и новых файлов — LF.
- Полный offline pytest с duckdb: 4635 passed, 4 skipped, 38 deselected, exit 0. После
  записи этого числа в доки повторены docs-тесты.

Границы. Наблюдения момента вне ключа по решению: второй прогон с другими записанными
результатами, другими показаниями или другим `created_at` делит `run_id` первого и в том же
каталоге evidence отклоняется; `decision verify` без `--created-at` берёт время с часов,
поэтому его повтор в один каталог отклоняется и без единого изменения. Части ключа в bundle
не записаны: manifest называет `run_id`, а из каких входов он выведен, можно пересчитать по
входам, но не прочитать из evidence. Ключ покрывает вход целиком: review rationale verified
asset или комментарий в `model.yaml` дают другой прогон с теми же проверками. Validation
report называет каждый продукт и контракт validated paths и несёт их issues, поэтому контракт
чужого продукта в этих путях двигает `run_id` этого продукта — и, как до среза, его
`contracts.validate`: issue чужого продукта грейдится на прогоне этого. File-level issue
отчёта называет файл путём, которым он прочитан: те же контракты из другого каталога — другой
отчёт и другой `run_id`. `decision verify` передаёт гейту dashboard specs, запинненные
продуктом, и verified assets, называющие его метрики; файл вне этого выбора `run_id` не
двигает. Валидный dashboard spec с non-finite значением фильтра, целым за пределом double или
одиночным суррогатом в title по-прежнему останавливает прогон в `bi.contract` необработанной
`CanonicalizationError`. Точный текст входа — внутренность ключа: в bundle нет ни его, ни его
digests, evidence остаётся RFC 8785. BI и DWH не запускались: проверка offline. Независимого
ревью у среза нет — ни модельного, ни человеческого.
