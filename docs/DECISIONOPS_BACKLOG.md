# DecisionOps — бэклог после финишной черты

Сюда идут находки ревью и прогонов вне пунктов F1–F6
[ADR 0010](adr/0010-finish-line.md). Запись не открывает срез: работа по ней начинается только
новым решением владельца. Сразу чинится лишь неверный вердикт по числам (ADR 0010, п. 2).
Решение 2026-11-13 ([ADR 0012](adr/0012-post-finish-development.md)) берёт в работу записи о
типах (D1), об отношениях и отказах (D2) и о покрытии dbt (D4); закрытая запись удаляется из
бэклога в срезе, который её закрыл. Что берёт план 2026-11-17 — таблица пункта 8
[ADR 0013](adr/0013-entry-points-to-proven-path.md).

Формат записи: дата, источник (срез, раунд ревью или прогон), что найдено, почему не исправлено
сразу. Новые сверху.

## 2026-11-18 — E4a, отрисованный SQL Superset

- **Superset 6.1: сохранение из UI пишет ключи `form_data` вне известного набора** (источник:
  [запись E4a](pilot/2026-11-18-e4a-rendered-sql/README.md), раздел «Superset 6.1»). `pie`
  получает `matrixify_*`, `heatmap_v2` — `border_color`, и чарт, типизированный на 4.1.2,
  читается как SQL. В примерах 6.1 к тому же нативные фильтры и ключ `bar_stacked` (`limit`
  отказывает и на 4.1.2): на C1 типизированы 2 чарта из 102 против 6 из 110 на 4.1.2. **Почему не исправлено сразу:**
  pin — 4.1.2, поддержка 6.1 — отдельное решение (запись E4a, «Ответ», п. 7); неизвестный ключ
  оставляет завышенное чтение, вердикт не меняется.
- **Область не отличает сохранение из UI от REST-сохранения после автозаписи Explore**
  (источник: проба REST записи E4a, ревью r1). `PUT` неизменённых `params` ставит
  `last_saved_at`, а `query_context` остаётся записанным Explore без умолчаний контролов: 8 из 8
  таких чартов примеров 4.1.2 в области, SQL GET расходится с дашбордом сортировкой, набор
  чтений совпадает. **Почему не исправлено сразу:** в трёх GET инвентаря нет признака
  происхождения `query_context`; E4b берёт из области только набор чтений, а в нём расхождений
  не измерено.
- **Область отрисованного SQL не проверена на слоях аннотаций, импорте, Superset 5.x и
  REST-сохранении на 6.1** (источник: запись E4a, раздел «Не сделано»). Слой аннотаций исключён
  из области по построению. Импорт не мерился, и исход неизвестен в обе стороны: если он ставит
  `last_saved_at`, импортированный чарт может попасть в область с `query_context` источника,
  если нет — остаётся вне её. 5.x не поднимался; REST-сохранение после автозаписи мерилось
  только на 4.1.2. Правило выведено и проверено на одних корпусах, в области 4 чарта на версию.
  **Почему не исправлено сразу:** каждое — свой прогон стенда.

## 2026-11-18 — E3, снимок инвентаря со стенда

- **Плитка с SQL-метрикой-отношением не типизируется** (источник: живой снимок E3,
  [запись](pilot/2026-11-18-e3-inventory-snapshot/README.md)). Чарт «Маржа по регионам» с
  ad-hoc метрикой `SUM(gross_margin) / SUM(revenue)` читается как SQL: в IR есть мера с
  `denominator`, но инвентарь типизирует только `AGG(column)`. На снимке примера смена
  timezone `gross_margin_pct` называет дашборд, а плитку маржи — только гэпом
  (`chart.sql_partial`, `chart.metric_unread`), не `computes_metric`. На ручной спеке E2 та же
  плитка была названа. **Почему не исправлено сразу:** точность чтения — E4b
  ([ADR 0013](adr/0013-entry-points-to-proven-path.md)); вердикт не меняется, `block` остаётся.
- **Чарт без сохранённого `query_context` теряет колонку `x_axis`** (источник: стенд E3).
  Superset 4.1.2 обрезает ответ датасетов дашборда до колонок, которые называют чарты; без
  `query_context` считаются только legacy-ключи `form_data`, и `x_axis` туда не входит. Бар,
  созданный через API, инвентарь читал как SQL с причиной «a column the dataset answer does not
  describe», пока на стенде не сохранили `query_context`, как это делает UI. E4a подтвердил:
  чарт, созданный через REST, остаётся без `query_context`, пока его не откроют в Explore или
  не сохранят из UI ([запись](pilot/2026-11-18-e4a-rendered-sql/README.md)). **Почему не
  исправлено сразу:** чтение `x_axis` без `query_context` — E4b; отказ типизации консервативен,
  вердикт не меняется.
- **Версия ref длиннее 4300 цифр — `ValueError`, а не `RefError`** (источник: r1 ревью E3, P2).
  `ContractRef.parse` в `auto_bi/refs.py` зовёт `int()` на `@N`, и Python отказывает в
  преобразовании такой строки обычным `ValueError`. Вызывающий, который ловит только `RefError`,
  кончается traceback'ом. Инвентарь (`--dashboard`, `--map`) с E3 отвечает exit 2. **Почему не
  исправлено сразу:** `refs.py` разбирает refs всего гейта; смена класса исключения там — правка
  поведения `verify` вне E3, вердикт по числам не меняется.

## 2026-11-17 — E1

- **Типизированный чарт с кавычкой в имени таблицы обрывает `verify` без bundle**
  (источник: r1 ревью E1, P1). Имя из семантической модели, например `dm.x'`, проходит

  Воспроизведение: модель с такой таблицей и один типизированный чарт на ней — `verify`
  кончается `TokenError` из `compile_contract → generate_source_sql → exp.to_table`.
  **Почему не исправлено сразу:** прежний дефект вне четырёх записей E1; вердикт по числам
  не меняет, учётные данные и сеть workflow не открывает. По п. 4
  [ADR 0013](adr/0013-entry-points-to-proven-path.md) публикацию не держит; исправление —
  отдельным решением владельца.

## 2026-11-17 — оценка `holistics/anfra`: не берём

- **Что смотрели**: `github.com/holistics/anfra` (Apache-2.0, v0.21.0) — фреймворк BI-приложений,
  которые пишет кодинг-агент поверх семантического слоя AMQL, с lineage и шкалой доверия в
  Inspect. Рассматривали как источник кода, как цель интеграции и как источник идей.
- **Решение**: не брать на вооружение. Причины: компилятор AML/AQL, lineage и исполнение SQL —
  закрытые бинарники из приватных репозиториев Holistics, открыта только оболочка на Go/TS;
  семантика только AMQL, а у нас dbt и свои контракты; проверки «изменение семантики не ломает
  числа» и evidence у anfra нет — gate её дополняет, а не повторяет; вне скоупа RU (Superset,
  DataLens).
- **Если вернуться**: плитка anfra-приложения сама называет датасет и метрику — для chart impact
  это `computes_metric` без непрозрачного SQL. Идея из их доков: одно описание команды для CLI и
  MCP (у нас аргументы MCP в `auto_bi/mcp/tools.py` описаны отдельно от argparse).

## 2026-11-14 — D6b, инвентарь Superset

- **Точный составной читающий SQL** ([spec](specs/superset-inventory.md)). Нетипизированный
  чарт читается как `SELECT *` плюс все SQL-фрагменты чарта и все сохранённые метрики и
  вычисляемые колонки датасета: заведомое завышение, гейт называет плитку `chart.sql_partial`.
  Не сделано: «второй уровень», называющий ровно те колонки, что читает не-типизированный viz,
  — по viz отдельно.
- **Отрисованный SQL и сохранённый `query_context`.** `GET chart/{id}/data?type=query` отвечал
  400 для 109 из 110 чартов `load-examples` на стенде (2026-11-14). E4a измерил область, где
  этот SQL читает то же, что SQL дашборда: последняя запись чарта — сохранение (из UI или
  любым REST-`PUT`), `query_context` согласован с `params` и датасетом, не legacy, без Jinja,
  нативного фильтра в области чарта, сравнения во времени и слоя аннотаций — 4 из 44 чартов
  своего корпуса на каждой версии, ни одного из примеров как загружены. В области GET называет
  все колонки SQL дашборда и ни одной лишней; текст совпал у 8 чартов, сохранённых из UI, и
  расходится сортировкой у 8 примеров, сохранённых по REST после автозаписи Explore
  ([запись](pilot/2026-11-18-e4a-rendered-sql/README.md)). Не сделано: чтение набора колонок в
  этой области — E4b.
- **Нативные фильтры дашборда не отображаются в IR**: чарт, к которому применяется нативный
  фильтр, читается как SQL (`chart.sql_partial`), даже если сам он IR-формы. Не сделано:
  значение фильтра выбирает зритель, у IR ему нет формы. Сужение до фильтров с дефолтом — вопрос
  политики: плитка читается такой, какой её открывает дашборд, а кросс-фильтры (включены по
  умолчанию) и выбор зрителя не читаются вовсе.
- **Row-level security не читается**: три GET её не показывают, а числа плитки она меняет по
  зрителю. Не сделано: правила RLS — отдельный API и роли, инвентарь читает дашборд, не зрителя.
- **`order_desc`, `sort_by_metric` и `sort_x_axis`/`sort_y_axis` heatmap читаются как
  отображение**: типизированная плитка сверх своего `row_limit` показывает строки, которые
  выбирают они. Не сделано: у IR нет порядка строк; что считает каждая строка, они не меняют.
- **Лишние отказы типизации** (аудит Superset 4.1.2, 2026-11-14): Superset дал бы те же числа, а
  чарт читается как SQL — pivot с оставшимся `groupby`; `row_limit` строкой или 0; `IN` со
  скалярным значением; только один из `resample_method`/`resample_rule`; `comparison_type` при
  пустом `time_compare`; фильтр `TEMPORAL_RANGE` при `time_range: No filter`; `all_columns` при
  `query_mode: aggregate`; ключи отображения вне `_DISPLAY` (`currency_format`, `show_value`,
  `zoomable`, `roseType`, `show_total`, `transposePivot`, `cache_timeout` и др.). Не сделано:
  каждый случай — своё чтение исходников 4.1.2 и тест; ложный `sql_partial` безопаснее ложного
  `computes_metric`.
- **Компилятор v1 пишет не тот запрос, что говорит типизированная спека** (эмпирический аудит,
  2026-11-14): `SupersetContractCompiler` не переносит фильтры и зерно IR в `form_data`, двум
  мерам по одной колонке даёт одну метку (Superset посчитает первую), колонку с точкой в имени
  читает как квалифицированную. Для гейта не важно — impact читает IR, а не компиляцию. Не
  сделано: это v1-путь сборки дашборда, не инвентарь.
- **`--database` не обязателен**: без него база Superset чарта не сверяется, только пишется в
  `inventory.json`. Не сделано: какую базу описывает модель, знает оператор — в `model.yaml`
  её нет.
- **Не больше 12 чартов** (`DashboardSpec`): дашборд крупнее отказывается целиком (2 из 11 на
  корпусе примеров — 21 и 24 чарта). Не сделано: снять лимит — изменение IR, вопрос владельцу.
- **Датасет без схемы** отказывает дашборд. Не сделано: источник читается как `schema.table`.
- **`COUNT(*)` не типизируется**: в IR нет меры `COUNT(*)`, чарт читается как SQL.

## 2026-11-14 — D5, read-only MCP

- **Сервер не песочница** ([spec](specs/mcp-server.md)). Пути инструментов читаются как в CLI:
  от рабочего каталога сервера, правами запустившего, через ссылки. MCP roots клиента не
  запрашиваются и пути ими не ограничиваются. Не сделано: ограничение корнем меняет ответ
  `_dashboard_file` и чтение контрактов, которые ссылками выходят наружу, — отдельное
  решение для CLI и MCP вместе.
- **Нет `--dwh` в MCP.** `verify` через MCP всегда offline, шаг 7 — `check.not_configured`. Не
  сделано: проба движка из вызова агента — сетевой доступ с учётными данными оператора; нужна
  граница, кто и когда его включает.
- **Тексты отказов называют флаги CLI**: `--product`, `--run`, `--created-at`,
  `--environment`, `--base-semantic-manifest` в отказах use case. Агент видит имя флага, а не
  аргумента инструмента. Не сделано: тексты общие с CLI, и их держат тесты CLI.
- **Нет `outputSchema`, Tasks extension, прогресса, отмены и HTTP-транспорта.** Запросы
  обслуживаются по одному, по порядку; долгий `verify` держит клиента. Не сделано: схемы
  ответов — pydantic-модели отчётов с их версиями; Tasks — когда появится долгая операция.
- **`pin`, `capture`, `investigate` — не инструменты.** `capture` исполняет SQL на движке и в
  read-only сервер не входит; `pin` и `investigate` агенту D5 не нужны.

## 2026-11-14 — D4b, derived-метрики

- **Форма формулы для derived** (`typed_derived`). Derived-метрика остаётся `external_ref`:
  частное входов — `derived.quotient`, остальное — `type.derived` (review). MetricFlow
  0.213.0 пишет выражение как написано — без `NULLIF` и приведения, — и на PostgreSQL ноль в
  знаменателе под числителем не NULL роняет запрос, а два целых терма делятся нацело
  ([отчёт D4](reviews/DECISIONOPS_DBT_COVERAGE_2026-11-13.md)). Не сделано: типизированное
  выражение над метриками меняет контракт формулы — отдельный ADR и паритет для него;
  владелец выбрал узкий D4b.
- **Входы derived не читаются.** Filter, offset_window и offset_to_grain входа derived-метрики
  гэпа не дают: метрика и так не разрешается, один гэп — на `expr` или на `type`. Не сделано:
  нужно только вместе с формой формулы для derived.
- **Derived-частное на ClickHouse не пробовалось.** Причина гэпа говорит только о PostgreSQL.
  Не сделано: строка гэпа одна на всех движках, и review от пробы не изменится.

## 2026-11-13 — D4a, V2-строки паритета

- **Отношение legacy- и V2-терма не доказано** (`parity.ratio-dialects`, review). Прогон
  паритета держит по проекту на диалект, корпус разбирает каждый диалект отдельным проектом.
  Не сделано: нужен проект прогона с метриками обоих синтаксисов и его строки; как dbt-core
  1.12.6 пишет такой проект, не проверялось.
- **Причина гэпа у слова-значения** (P3 ревью r1). `null` или `true` вместо колонки (имя
  меры или V2-метрики, `expr`) — гэп конструкции с причиной «a column that is not one lower-case
  identifier», хотя по форме это такой идентификатор; код, severity и путь верны. Не
  сделано: своя причина для слов-значений меняет ответ резолвера в записях корпуса —
  нужен перепрогон корпуса.
- **Выдержка отказа dbt без `[WARNING]`/`[ERROR]`** (P3 ревью r1,
  `scripts/dbt_corpus.py`, `_excerpt`). Без такой строки выдержка идёт с начала вывода и
  кончается перед первым traceback: вывод, который с traceback начинается, даёт пустую
  выдержку, и текст исключения теряется. В корпусе и записях F4 такого вывода нет. Не
  сделано: строка исключения после traceback без путей прогона.

## 2026-11-13 — D2, отношения и отказы

- **Сервер внешней таблицы не ответил на чтение.** Внешняя таблица PostgreSQL с D2 — витрина, и
  читает её сервер обёртки: `file_fdw` без файла отвечает `58P01`, и прогон кончается exit 2
  ошибкой в одну строку, как при любом состоянии вне набора отказов; другие обёртки
  (`postgres_fdw` с недоступным сервером) живьём не проверялись. Не сделано: это не неверный
  вердикт, а конец прогона без bundle; читать такие состояния как `access.table_unreadable` —
  новое правило со списком состояний каждой обёртки.
- **Гранты записи обёртки, которая не пишет.** Гранты записи внешней таблицы считаются, как у
  таблицы: `postgres_fdw` пишет через них. `file_fdw` отвечает на любую запись `0A000`, но роль с
  такими грантами получит `access.role_writable` (block). Не сделано: ошибка в сторону block, а
  различать обёртки по способности писать — каталог обёрток и их версий.
- **Чужая сторона внешней таблицы.** Гранты и row security пользователя, под которым сервер
  внешней таблицы ходит к источнику, не наблюдаются: `dwh.access` и `dwh.security` оценивают
  то, что о внешней таблице говорит локальный каталог. Не сделано: у каждой обёртки свой
  источник и свой способ спросить, а `postgres_fdw` живьём не проверялся.

## 2026-11-13 — D1, имена типов

- **Классы паритета и точность доли читают тип как написан.** `dwh.physical` с D1 сравнивает
  тип по имени, которое печатает движок, а `_PG_CLASSES` и `CLICKHOUSE_CLASSES`
  (`semantic/metricflow_formula.py`) — по написанию: у `dec(18,2)`, `serial`, `"int4"`,
  `pg_catalog.int8` на PostgreSQL и у `BIGINT`, `DECIMAL(18,2)`, `Nullable(BIGINT)` на ClickHouse
  класса нет, и строка паритета уходит в гэп (review). Правило точности доли в `sql_contract` на
  PostgreSQL читает имя движка с D1, а на ClickHouse — написание, как классы паритета: член
  `sum()` по колонке `BIGINT` даёт ложную advisory-находку `sql.ratio_inexact_term`. Не сделано
  в D1: классы паритета — правило другой проверки, его разумно менять вместе с покрытием dbt
  (D4); ошибка — в сторону review.
- **Типы ClickHouse вне правил D1** — `Tuple`, `Enum`, `Nested`, `AggregateFunction`, `TIME`
  (24.8 читает его как `Int64`, поздние версии — как свой тип `Time`) и другие семейства, которых
  нет в таблице: другое написание такого типа сравнивается как написано, `physical.type_drift`
  (review). Не сделано: их аргументы — не типы и не числа (имена полей, значения перечисления,
  функции агрегата), а в колонках витрин они редки.
- **Редкие написания вне правил D1** (найдены ревью r1 и пробами): на PostgreSQL — имя массива
  `_int4` (`format_type` печатает `integer[]`), `interval(n)` при n ≥ 6 (печатает `interval(6)`,
  без точности — `interval`), пробел, опущенный перед `with`/`array`, литералы PostgreSQL 16 в
  модификаторе (`0x14`, `1_8`), модификатор строкой (`numeric('18','2')`), модификатор типа
  расширения (`"geometry"(Point,4326)`); на ClickHouse — ширина целого из 20 и более цифр
  (`INT(99999999999999999999)` 24.8 принимает как `Int32`), пустой пояс `DateTime('')` (печатает
  `DateTime`), запятая в конце аргументов (`Decimal(18, 2,)`), пояс в другом регистре
  (`DateTime('utc')` против `'UTC'`: движок печатает как написано). Сравниваются как написаны —
  `physical.type_drift` (review). Не сделано: движок их принимает, но модели их почти не пишут;
  ошибка — в сторону review.

## 2026-11-10 — F4, формулы публичных dbt-проектов

- **Узкое подмножество типизированной формулы на реальных проектах.** На трёх проектах dbt-labs
  (MetricFlow tutorial, jaffle-sl-template, jaffle-shop) из 54 метрик гэпов проекта нет у
  десяти после D4a (в F4 — у четырёх), и с контрактом на своей таблице разрешилась бы каждая
  из десяти. Остальные 44 останавливает гэп проекта — выражение меры или V2-метрики, которое
  не одна колонка, время из выражения, фильтр метрики, derived и cumulative, `median`,
  `percentile`, `sum_boolean`, `fill_nulls_with`, `join_to_timespine`
  ([отчёт D4a](reviews/DECISIONOPS_DBT_COVERAGE_2026-11-13.md)). Каждый такой гэп — строка
  инвентаря (review), неверного вердикта нет. D4b дал derived-частному свою строку
  (`derived.quotient`), мера та же. Не сделано: новая поддержка конструкций и паритет для
  них, вне ADR 0012.
