# Unreadable run inputs: a run input a command cannot read is a usage error — проверки автора

**Дата:** 2026-10-04
**Срез:** T-51; verifier 92 / check 67 (без изменений)
**Автор:** Claude Opus 5.5 (`claude-opus-5-5`), напрямую, без MyFlow-исполнителей
**Модельное ревью:** не проводилось

Владелец в этой сессии выбрал прямое исполнение: спеку, код, тесты и доки написал Claude
Opus 5.5, MyFlow не запускался, synthetic Astra xhigh review не было. По
[ADR 0006](adr/0006-modelled-review-development-gate.md) модельное ревью не выполнено, пока
нет фактического результата Astra xhigh, — у этого среза его нет. Всё перечисленное ниже —
проверки автора над собственной работой: не независимое ревью, не human/design-partner
acceptance и не production acceptance. Тесты и пробы прогонялись на Mac (Python 3.13.13 и
3.12.13, PyYAML 6.0.3). Контракт: [files a command cannot read](specs/unreadable-inputs.md).

Предыдущий срез сделал файл контракта, который не читается, finding'ом. `decision verify`
получает не только контракты: `model.yaml` base и candidate refs, dashboard specs, verified
assets и recorded results; `decision capture` читает verified assets и `model.yaml` candidate
ref. Контракт, который не читается, оставляет остальной прогон для грейда. Без одного из этих
файлов грейдить нечего — нет snapshot для diff, spec для компиляции, asset для выбора или
результата для сверки, — поэтому такой файл не finding, а usage error: команда называет файл
и причину и выходит с `2`. Так уже отвечали dashboard spec и results с синтаксической ошибкой.

На HEAD `43869e8` воспроизведено настоящим CLI как процессом: прогон, который проходит, и
одна порча одного файла — восемь строк предыдущего среза, последовательность, которая не
закрыта, байты не-UTF-8, файл со списком, с текстом, пустой, с mapping, которую схема
отвергает, файл без права чтения. Пять файлов на 15 порч — 75 прогонов `decision verify`:
44 кончились traceback и exit 1, 30 — exit 2, один — exit 4 (пустой `model.yaml` base — модель
ни о чём, она грейдится):

- `model.yaml` base и `model.yaml` candidate — по 14 из 15;
- dashboard spec — 3: строки с `KeyError`, `AttributeError` и `RecursionError`. Пять строк с
  `ValueError` отвергались как `… is not a valid DashboardSpec: day is out of range for
  month` — отказ интерпретатора под именем схемы;
- verified asset — 5: те же три строки, незакрытая последовательность и файл без права
  чтения. Остальное отвергалось под путём, с которого грузились assets, а не под файлом;
- recorded results — 8: все строки, которые не строятся.

`decision capture` над asset и `model.yaml` candidate — 30 прогонов, 6 traceback: те же три
строки в каждом из двух файлов. Путь `--evidence`, который оказался файлом, каталог evidence
без права записи и путь под каталогом без права записи — три traceback из трёх
(`NotADirectoryError`, `PermissionError`, `PermissionError`).

Теперь вход прогона читает общий загрузчик предыдущего среза. Файл, который не открывается, не
является UTF-8, который PyYAML отвергает или не может построить, кончает `decision verify` и
`decision capture` до грейда, до вопросов движку и до записи: `error: cannot read <файл>:
<причина>`, exit 2, одна строка в stderr, stdout пуст; каталог evidence не создан, запрос не
открыт, output не записан. Причина — одна строка: класс брошенного; ` at line <n>, column
<m>` (счёт с единицы) там, где PyYAML даёт позицию; ` (<класс>: <сообщение>)` — что сказал
интерпретатор — там, где документ не построился, с пробелами и переводами строк, сведёнными
к одному пробелу. Строка печатается и нигде не запечатывается, поэтому, в отличие от finding
предыдущего среза, может цитировать файл: позиция и сообщение — единственные указатели на
значение.

Контракт метрики в semantic ref, который файловая система не даёт открыть, кончает прогон так
же, под своим путём. Открытый и непрочитанный контракт остаётся gap с digest байтов файла; у
неоткрытого байтов нет, и отказ файловой системы говорит о машине, на которой идёт прогон, а
не о ref. Так же назван путь, на который команде нельзя посмотреть: `model.yaml` ref, его
каталог metrics и файл под путём assets, пока файлы перечисляются.

Файл, который прочитан и не то, чем должен быть, — usage error под своим именем: `<файл> is
not a valid semantic model: …` для `model.yaml` со списком, текстом или mapping, которую
схема отвергает; `<файл> is not a valid verified asset: …` для файла под assets. Два assets
одного id — вина не одного файла, и они остаются `<путь assets> holds an invalid verified
asset: duplicate verified asset id: <id>`. `<файл> must contain a mapping` для spec, results
и пустого `model.yaml` candidate — как прежде. `VerifiedAssetRepository.load` бросает
`VerifiedAssetFileError` — `ValueError` с файлом в тексте и брошенным как cause.

Ref, чьи файлы прочитаны и приняты схемами, но держат значение, с которым его граф не
строится или не адресуется, — `cannot load semantic ref <ref>: …` и текст отказа. Какой файл
держал значение, отказ не знает, поэтому файл не назван, а `model.yaml` называется невалидным
только за то, что отвергла схема самой модели. Воспроизведено одиночным суррогатом — YAML
держит его как escape `"\ud800"` в двойных кавычках, PyYAML его строит: в описании таблицы
модели и в описании контракта метрики use case на HEAD бросал `CanonicalizationError` (у
digest графа нет для него формы), в dimension и в ключе grain контракта — `ValidationError`
схемы gap, который не может его процитировать.

Store отвечает на отказ файловой системы своей `ArtifactStoreError` с отказом как cause:
`cannot write '<path>' of run '<id>': <класс>`, `cannot read '<path>' of run '<id>'` и
`cannot look for '<path>' of run '<id>': <класс>` — «посмотреть не удалось» не читается как
«нет». `decision verify` отвечает `error: cannot write the evidence bundle under <каталог>:
…` и выходит с `2`. Manifest пишется последним, поэтому записанное до отказа bundle не
является: `decision evidence` его не находит, а тот же прогон после устранения причины пишет
bundle с тем же run id и тем же evidence digest, что и прогон без отказа.

Версии evidence не менялись (92/67): прочитанный вход читается как прежде, и ни один вход,
дававший bundle или captured result, не даёт другого. Четыре отказа, которые и на HEAD были
usage error, читаются иначе: синтаксическая ошибка в spec и results получила позицию;
`ValueError`-строки в spec отвергаются как `cannot read …: ConstructorError (ValueError: …)`,
а не как невалидный `DashboardSpec`; файл под assets назван сам, а не путь, с которого
грузились assets; `decision capture` говорит о candidate ref словами `decision verify`, а не
`cannot load candidate semantic ref <ref>: …`.

Выбор. Границу назвал предыдущий срез: `model.yaml`, verified assets, dashboard specs и
recorded results «по-прежнему могут кончиться traceback на тех же значениях». Срез выбрал
оркестратор, Astra-выбора по ADR 0006 для него нет. Решения внутри среза — тоже автора:

- Usage error, а не finding: finding запечатывается в bundle о прогоне, а без такого файла
  прогона не было. Тем же кодом уже отвечали spec и results с синтаксической ошибкой.
- Одна функция причины (`unread_reason`) для строки, которая печатается. Finding, который
  запечатывается, по-прежнему несёт только класс.
- Контракт ref, который не открывается, кончает прогон, а не становится gap: gap несёт digest
  байтов, которых нет. Под validated paths такой файл остаётся `contract.unreadable` —
  асимметрия записана в границах.
- `VerifiedAssetFileError` остаётся `ValueError`: кто ловил `ValueError` от репозитория,
  ловит и её. Кто ловил именно `ValidationError` схемы, больше её не ловит: она стала cause.
  В пакете так не ловит никто; так ловил один существующий тест
  (`tests/test_sql_guard_parse_depth.py`, глубина парсера в reviewed-запросе asset), и первый
  полный gate среза упал на нём: 2 failed, 4944 passed. Тест теперь ждёт
  `VerifiedAssetFileError` с `ValidationError` в cause; его проверки текста отказа не тронуты.
- Store не выпускает `OSError`; отказ взгляда в `exists` — ошибка, а не `False`.
- `OSError` ловится у каждого входа отдельно, не общим `except` в CLI: отказ соединения с
  движком должен идти своим путём, и вопрос среде остаётся вне этих guard'ов.
- Три дефекта собственной работы найдены самопроверкой и исправлены до коммита, каждый закрыт
  тестом и мутантом: любой `ValueError` snapshot'а приписывался `model.yaml`, включая отказ
  digest графа из-за контракта рядом; взгляд на `model.yaml` и на файл под assets остался вне
  `try`, и `decision capture` кончался traceback там, где HEAD отвечал exit 2.

Границы. Срез закрывает чтение. Взгляд на путь закрыт только внутри semantic ref, среди
файлов под путём assets и внутри каталога evidence. Под каталогом, в который нельзя войти,
по-прежнему кончают traceback: файл validated-контракта (`decision verify` и `decision
validate`), сам путь assets (`decision verify` и `decision capture`), dashboard spec и
recorded results (`decision verify`), output (`decision capture`) — семь прогонов пробы.
Каталог, который нельзя перечислить, читается как пустой — шесть прогонов пробы: с
каталогом assets `decision verify` выходит с 0 и `pass_with_advisory`
— asset не выбран, и ничто не говорит, что его не удалось выбрать; с каталогом metrics base
ref — exit 3, candidate ref — exit 4, оба на snapshot без метрик; с validated-каталогом —
exit 2 `no decision product contract found in the given paths`, так же `decision validate`;
`decision capture` с каталогом assets — exit 2 `no verified asset under <путь>`. Контракт,
который файловая система не даёт открыть, — finding под validated paths и usage error в ref:
отчёт валидации отвечает за свои пути, будет за ним прогон или нет, а snapshot говорит, с
каких байтов он снят. Под путём assets загружается каждый файл, включая assets других
продуктов: один непрочитанный файл кончает прогон каждого продукта — как всегда кончал файл,
который отвергла схема. `cannot load semantic ref <ref>: …` несёт текст отказа как есть —
место значения в графе или сообщение схемы, против которой не пишется ни один файл; значение
не грейдится как gap своего файла. То же значение под validated paths не закрыто: одиночный
суррогат как dimension validated-контракта метрики кончает use case `decision verify`
`ValidationError` схемы gap. Запись manifest — одна и последняя, но не атомарная: manifest,
обрезанный наполовину, даёт на повторе exit 2 `run '<id>' already holds bundle …; refusing to
overwrite it with …`, а `decision evidence` — exit 4 `verdict: block (1 problem(s))`. Строка
usage error может цитировать файл: сообщение значения, которое не построилось, и текст схемы
о модели или asset, которые она отвергла; строка печатается в stderr и не запечатывается.
Отказы файловой системы в тестах модуля — подмена методов `Path`, а не права на файлы: тесты
не зависят от того, под кем идут. Настоящие права проверены процессными пробами на macOS;
семантика прав Windows не проверялась. Входы `decision investigate` и загрузчики v1-раннтайма
читают YAML сами и не тронуты. BI и DWH не запускались: проверка offline. Независимого ревью
у среза нет — ни модельного, ни человеческого.
