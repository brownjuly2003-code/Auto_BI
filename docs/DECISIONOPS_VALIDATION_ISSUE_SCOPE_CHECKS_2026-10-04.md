# Validation issue scope: a run grades the verified product's issues — проверки автора

**Дата:** 2026-10-04
**Срез:** T-48; verifier 92 / check 67
**Автор:** Claude Opus 5.5 (`claude-opus-5-5`), напрямую, без MyFlow-исполнителей
**Модельное ревью:** не проводилось

Владелец в этой сессии выбрал прямое исполнение: спеку, код, тесты и доки написал Claude
Opus 5.5, MyFlow не запускался, synthetic Astra xhigh review не было. По
[ADR 0006](adr/0006-modelled-review-development-gate.md) модельное ревью не выполнено, пока
нет фактического результата Astra xhigh, — у этого среза его нет. Всё перечисленное ниже —
проверки автора над собственной работой: не независимое ревью, не human/design-partner
acceptance, не измерение времени человека и не production acceptance. Тесты и пробы
прогонялись на Mac (Python 3.13.13); на Windows запускалась одна проба записи пути.
Контракт: [the validation issues a run grades](specs/validation-issue-scope.md).

`decision verify` загружает каждый контракт validated paths и валидирует каждый продукт,
который там находит, а верифицирует один: `--product` называет его, когда продуктов
несколько. Validation report — один на все пути: refs продуктов и контрактов метрик и issues
всех продуктов. Четыре из пяти tracked pilot-пакетов держат по два продукта в одном каталоге
контрактов, так что один отчёт за несколькими продуктами — обычная раскладка. Остальные
проверки гейта и до среза отвечали за один верифицируемый продукт (ARCHITECTURE §8.3); шаг 1,
`contracts.validate`, грейдил каждый issue отчёта. Границу «issue чужого продукта грейдится
на прогоне этого» записали спека и проверки T-47. На HEAD `25b620c` через входы
`decision verify` воспроизведено для продукта `decision://sales/weekly_margin@1` — один в
путях он даёт `contracts.clean` и вердикт `pass_with_advisory` — рядом со вторым продуктом
`decision://sales/monthly_margin@1`:

- второй продукт пиннит `metric://sales/gross_margin_pct@2`, а пути держат версию 3:
  `contracts.validate` первого — block с `contracts.issues`, единственный issue
  `metric_ref.version_mismatch` несёт source `decision://sales/monthly_margin@1`, вердикт
  прогона — `block`;
- второй продукт пиннит метрику без контракта (`metric_ref.unknown`) или режет по dimension,
  которую его метрика не объявляет (`dimension.not_allowed`): тот же block;
- второй продукт пиннит собственную метрику `metric://sales/revenue@3`, которой первый не
  касается: её контракт retired — block, draft — review и `needs_review`, deprecated — шаг
  advisory с `contracts.issues`;
- второй продукт верифицируется под policy, под которой его метрика не governed
  (`policy.mismatch`): review и `needs_review`.

В каждом таком прогоне subject refs шага называли только первый продукт и его pin, и ничего
в первом продукте, его метрике или любом из двух refs нельзя было изменить, чтобы снять
finding.

Теперь issue отчёта — *чужой*, когда отчёт называет верифицируемый продукт среди `products`,
называет там же `source` этого issue и два ref различаются. Чужой issue не грейдится: он не
двигает ни status, ни summary code шага, ни вердикт прогона. Он запечатан отдельно, в
`other_product_issues`, без изменений и в порядке отчёта; ключ есть всегда, без таких issues
это `[]`. `issues` payload — грейдящиеся issues отчёта в его порядке, затем pin и rule issues;
`verdict` payload — вердикт `issues`. Detail продолжен перед `;` счётчика pins:
`, <x> issue(s) of <y> other product(s) not graded`, где `<y>` — число разных продуктов,
которые называют отложенные issues. Всё остальное грейдится, как прежде: issues
верифицируемого продукта, issues загрузки файла (`contract.unreadable`,
`contract.unknown_kind`, `contract.invalid`, `contract.duplicate_id`), отчёт, не называющий
верифицируемый продукт, — целиком, issue с `source` вне `products`. Validation report гейт не
меняет; `decision validate` прежний. `VERIFIER_VERSION` 91 → 92: те же входы дают другой
bundle и могут дать другой вердикт. `CHECK_VERSION` 66 → 67: шаг грейдится другим правилом.
Исторические bundles не переписаны.

Выбор. Срез закрывает границу, записанную в спеке и проверках T-47; его выбрал оркестратор,
Astra-выбора по ADR 0006 для него нет. Решения внутри среза — тоже автора:

- Чужой issue определяется по `source`, а не по коду или subject. Каждое validation rule
  отвечает за один продукт и пишет его ref в `source` каждого своего issue; issue загрузки
  файла несёт путь. Ничто из сказанного правилами об одном продукте не несёт ref другого:
  метрика, которую пиннят оба, даёт по issue на продукт (сценарий «a rule answered for both
  products»).
- Issues загрузки файла грейдятся на прогоне каждого продукта, включая сломанный или
  повторный контракт чужого продукта. Непрочитанный файл может оказаться вторым определением
  контракта, от которого зависит этот продукт, и отчёт этого не знает; решать по id, который
  объявляет сломанный файл, значит доверять сломанному файлу. Цена записана в границах.
- Отчёт, не называющий верифицируемый продукт, построен не для него: чужим в нём нечего
  назвать, и он грейдится целиком. Issue с `source`, которого нет в `products`, грейдится:
  неизвестный source — не свидетельство о другом продукте.
- Отложенные issues запечатаны, а не отброшены: bundle называет, что отчёт сказал о других
  продуктах, и detail шага их считает. Отчёт остаётся в idempotency key целиком (решение
  T-47 не пересматривалось), поэтому чужой issue двигает `run_id`.
- `decision validate` не тронут: он отвечает за пути целиком, и его exit code следует
  issues всех продуктов.

Проверки автора — на рабочем дереве среза, на Mac:

- Спека написана до кода: одно требование, сейчас 17 сценариев. Факты о HEAD сняты пробой
  до реализации. Статусы HEAD для retired, draft и deprecated метрики чужого продукта
  подтверждены пробой уже после реализации: в первой пробе контракт второй метрики был
  невалиден и давал `contract.invalid`. После реализации добавлены сценарий об отчёте,
  который задаёт собственный порядок, третий, чистый продукт в сценарии о счётчике
  продуктов, сценарий о exit codes CLI и строка summary в первом сценарии.
- Новый модуль `tests/test_validation_issue_scope.py` — 30 тестов в 18 функциях: по тесту на
  сценарий и тест версий. Против `auto_bi` из HEAD `25b620c`: 30 failed / 0 passed — каждый
  тест читает `other_product_issues`, которого payload HEAD не несёт. Чтобы отделить правило
  от формы payload, тот же модуль прогнан против копии HEAD, где в payload добавлен один
  этот ключ, всегда пустой: 19 failed / 11 passed. Прошедшие 11 — контроли, в которых
  откладывать нечего: шесть issues загрузки файла, несуществующий путь, один продукт в путях
  (два теста), отчёт без верифицируемого продукта, source вне `products`. Упавшие 19 — каждый
  сценарий, где у другого продукта есть issue, и тест версий. На рабочем дереве — 30 passed.
- 19 ручных мутантов `_issues_by_product` и `_check_contracts`, каждый — против нового
  модуля в отдельном worktree: убиты все 19. Мутанты: откладывать при отчёте, не называющем
  продукт; откладывать всё с другим source, включая issues загрузки; считать чужим любой
  source, записанный как ref; откладывать и собственные issues; считать в detail все
  остальные продукты отчёта либо issues вместо продуктов; сортировать отложенные issues (по
  subject; по source и коду) и грейдящиеся (по коду; по source); опускать ключ, когда он
  пуст; оставлять `verdict` payload вердиктом отчёта; класть в `issues` отчёт целиком; брать
  status, summary code или счётчик detail по отчёту целиком; убирать clause из detail,
  ставить её после pins, писать её всегда. Мутанты написал автор: они проверяют то, что
  автор догадался сломать, и не заменяют инструментальное mutation-покрытие.
- Проба через входы `decision verify` на HEAD и на рабочем дереве, 10 случаев: один продукт,
  два чистых продукта, семь rule issues второго продукта и обратный контроль — собственный
  `dimension.not_allowed` верифицируемого продукта рядом с чистым вторым. HEAD: block в
  четырёх случаях, review в двух, advisory в одном. Рабочее дерево: во всех семи
  `contracts.clean`, pass, вердикт `pass_with_advisory`, detail с
  `1 issue(s) of 1 other product(s) not graded`. Обратный контроль — block оба раза.
- Контроль на tracked pilot-пакетах: пять пакетов, 9 продуктов и chart-impact overlay —
  10 прогонов, в 9 из них в путях два продукта. Вердикт, status, summary code и detail
  каждой из 15 проверок совпадают с HEAD во всех 10 — кроме digest bundle, который цитирует
  detail `evidence.bundle`: он двигается с версией verifier и новым ключом payload.
  Грейдящиеся issues те же, `other_product_issues` — `[]` во всех 10, единственный
  добавленный ключ payload — он. Pilot-отчёты не несут ни одного validation issue, поэтому
  этот контроль показывает, что правило ничего не меняет там, где откладывать нечего, и
  само правило не упражняет.
- CLI, тестом: над путями с двумя продуктами, где второй пиннит ушедшую версию,
  `decision validate` — exit 4, `decision verify --product decision://sales/weekly_margin` —
  exit 0, `--product decision://sales/monthly_margin` — exit 4. На HEAD этот тест падает.
- Путь, записанный как ref: несуществующий validated path `decision://sales/monthly_margin@1`
  загрузчик называет так, как его пишет `Path`, — на Mac `decision:/sales/monthly_margin@1`
  (тест), на Windows `decision:\sales\monthly_margin@1` (проба, Python 3.13.7). Ни та, ни
  другая запись не равна ref продукта, и `contract.unreadable` грейдится. Сам модуль на
  Windows не запускался.
- Кто ещё читает отчёт: в `auto_bi` входы гейта `validation` читаются в двух местах — в
  idempotency key (целиком) и в `_check_contracts`. Другой проверки или рендера, читающего
  issues отчёта, нет; `reports/summary.md` получает detail шага в таблице «Every check» —
  первый сценарий проверяет строку.
- Изменённый существующий тест: `tests/test_run_identity.py::test_versions` ждёт версии не
  ниже 91 и 66 — прежде он закреплял точные значения и падал бы на каждом следующем срезе.
  Остальные существующие тесты не менялись.
- Спеки [product metric pins](specs/product-metric-pins.md) и
  [run identity](specs/run-identity.md): требование о payload шага и граница о чужом issue
  приведены к новому правилу.
- Ruff, Black и strict mypy (120 модулей) чистые; концы строк изменённых и новых файлов — LF.
- Полный offline pytest с duckdb: 4665 passed, 4 skipped, 38 deselected, exit 0.

Границы. Срез ослабляет гейт продукта: релиз, который verifier 91 блокировал или отправлял в
review из-за контракта другого продукта, теперь проходит. Репозиторий, которому нужно «ни
один продукт не выпускается, пока контракты любого в конфликте», гейтит на exit code
`decision validate`: он отвечает за пути целиком. Issues загрузки файла грейдятся на прогоне
каждого продукта: файл validated paths, который не разбирается, неизвестного kind, не проходит
схему или повторяет id, блокирует релиз каждого продукта этих путей — также когда это
контракт чужого продукта или метрики, которую этот продукт не пиннит. Чужой issue определяется
одним `source`, как его пишут validation rules; код issue не читается, и отчёту, построенному
не `decision validate`, гейт верит на слово. `<n> metric contract(s) resolved` по-прежнему
считает каждый контракт метрики validated paths, какой бы продукт его ни пиннил. `run_id`
двигается вместе с чужим issue: два прогона одного продукта, различающиеся только контрактом
другого, получают разные `run_id` при одном исходе. Отложенные issues видны в payload шага и
в его detail; отдельного раздела в `reports/summary.md` для них нет. BI и DWH не запускались:
проверка offline. Независимого ревью у среза нет — ни модельного, ни человеческого.
