# E4a: отрисованный SQL Superset как чтение плитки (2026-11-18)

Исследование E4a [ADR 0013](../../adr/0013-entry-points-to-proven-path.md). Вопрос: в какой
области отрисованный SQL — `GET /api/v1/chart/{id}/data?type=query` по сохранённому
`query_context` — даёт право назвать плитку прочитанной целиком. Эталон не зависит от читателя
гейта: SQL, который исполнил движок, когда дашборд открылся в браузере (ClickHouse
`system.query_log`, журнал statement PostgreSQL). Ветка `e4a-rendered-sql` от `main` `ad6d538`.
Код инвентаря, пишущий адаптер и его pin не менялись: в срезе только стенд, скрипты замера и эта
запись.

## Ответ

Область — шесть проверок по ответам, которые инвентарь получает без браузера (раздел «Область»).
В неё попадают чарты, последняя запись которых — сохранение, и `query_context` которых согласован
с чартом. На закреплённых корпусах это 4 из 44 чартов C2 на 4.1.2 и 4 из 44 на 6.1; на корпусе
примеров (C1) область пуста на обеих версиях: примеры загружены без `last_saved_at`, а
`query_context` им пишет только открытие в Explore.

- **Чтения.** У каждого чарта в области SQL GET называет все колонки, которые читает SQL
  дашборда, и ни одной лишней: 8 чартов C2 на двух версиях и 8 чартов примеров 4.1.2 после
  пробы с REST-сохранением. Пропущенных чтений в области — 0 во всех прогонах.
- **Текст SQL.** У 8 чартов C2, сохранённых из UI, GET назвал тот же SQL, что дашборд отправил
  движку и движок исполнил. У 8 чартов, которым `query_context` записал Explore, а потом их
  сохранили по REST без изменений, текст расходится сортировкой: у шести pie нет `ORDER BY`, у
  двух table — `ASC` вместо `DESC`. Инвентарь их не отличает: REST-сохранение тоже ставит
  `last_saved_at` (проба REST, раздел «Пробы»).
- **Вне области** GET пропускает чтения: 12 чартов C1 и 5 C2 на 4.1.2, 4 и 3 на 6.1. Каждый
  отсекают проверки `api` (legacy-viz) или `fresh` (`query_context` устарел). Совпадает же GET с
  дашбордом и вне области часто: 74 из 110 чартов C1 и 30 из 44 C2 на 4.1.2, 77 из 102 и 31 из
  44 на 6.1. Но без браузера этого не отличить: тот же по форме ответ дают чарты, у которых
  совпадения нет.

Решение для E4b:

1. Отрисованный SQL читается только в области и даёт набор чтений плитки, а не текст SQL
   дашборда: в области пропущенных и лишних чтений нет, а сортировка и `LIMIT` могут
   расходиться — так собирает запрос автозапись Explore (проба REST, «Где GET расходится»).
   Вне области остаются прежние уровни: типизированный и завышенный SQL с гэпом
   `chart.sql_partial`.
2. Отрисованный SQL даёт чтение, не метрику. Post-processing (`contribution`, `rank`, `pivot`,
   `rolling` и другие) Superset применяет в Python после SQL. Плитка из области — «прочитана
   целиком», но не `computes_metric`: post-processing есть у 1 из 4 чартов области C2 на 4.1.2
   и у 2 из 4 на 6.1.
3. Без `query_context` GET отвечает 400. Инвентарь его не создаёт: открытие чарта в Explore —
   запись, и Superset принимает её даже от зрителя без прав владельца (раздел «Без
   `query_context`»).
4. Датасет без схемы остаётся отказом: Superset не называет схему подключения ни в GET, ни в
   SQL дашборда (`FROM sales_daily` на обеих версиях).
5. На 6.1 GET показывает текст до прохода sqlglot, а движок исполняет текст после него
   (`count(` → `COUNT(`, `!=` → `<>`, `x IS NOT NULL` → `NOT x IS NULL`). Сравнение и разбор —
   после раунд-трипа sqlglot в диалекте базы.
6. RLS, параметры URL и выбор зрителя остаются гэпом «по зрителю». GET отрисован для учётной
   записи инвентаря и совпадает с тем, что дашборд исполняет для неё же. Правила RLS инвентарь не
   видит (их нет в трёх GET), поэтому RLS — общая граница спеки, а не проверка области.
7. Читатель v1 читает ответы 6.1 без ошибок формы, но типизирует меньше (раздел «Superset
   6.1»). Pin 4.1.2 не меняется; поддержка 6.1 — отдельное решение.

## Область

Плитка в области, когда выполнены все проверки:

| Проверка | Что читает инвентарь | Что закрывает |
|---|---|---|
| `saved` | список чартов: `changed_on_utc` и `last_saved_at` расходятся не больше чем на 2 с | `last_saved_at` ставит любое сохранение: из UI и любой REST-`PUT`, кроме автозаписи одного `query_context`, — в том числе `PUT` неизменённых `params` (проба REST). Автозапись `query_context` из Explore и загрузка примеров его не ставят. Не отсекает REST-сохранение после автозаписи: текст SQL расходится, чтения — нет. Автозапись собирает `query_context` из сырых `form_data`, без умолчаний контролов: pie и funnel без `ORDER BY`, `bubble_v2` с другим порядком метрик, `box_plot` и `waterfall` 6.1 с `LIMIT 50000` вместо 10 000 |
| `fresh` | `query_context.form_data` равен `params` по каждому ключу любой из сторон, кроме `slice_id`, `datasource`, `dashboards`, `url_params` и ключей запроса `force`, `result_format`, `result_type`; датасет `query_context` — датасет чарта в ответе `charts` дашборда и есть в ответе датасетов | `PUT params` по REST оставляет прежний `query_context`, и GET отрисовывает прежний запрос (проба stale). Ключ, удалённый из `params`, и смена датасета чарта — тот же механизм (живые пробы r2 и мутанты) |
| `api` | viz обслуживается `/api/v1/chart/data`; в замере — по запросам браузера | legacy `/superset/explore_json/` строит SQL своим кодом из `form_data`, а GET отрисовывает `query_context`, которым дашборд не пользуется |
| `plain` | нет `{{` и `{%` в SQL датасета и в `params`; нет нативного фильтра, в область которого входит чарт, с дефолтом или без. Фильтр охватывает чарт, если `scope.excluded` его не называет: `chartsInScope` не учитывается, вкладка не разбирается | Jinja отрисовывается для того, кто спрашивает. Нативный фильтр дашборд добавляет в запрос, GET — нет: дефолт значения и дефолт времени `extraFormData.time_range` (пробы), первое значение при загрузке и фильтр по вкладке (мутанты). Фильтр пробы, записанный через REST, хранит `chartsInScope: []`, а дашборд применяет его к обоим чартам |
| `answer` | GET 200, у каждого результата есть `query` и нет `error` | 6.1 отвечает 200 с `"error": "Empty query?"` у legacy `line` и `dist_bar`, сломанных сохранением |
| `single` | ни у одного запроса `query_context` нет `time_offsets` и `annotation_layers`; в `params` нет `time_compare` и `annotation_layers` | рядом с основным запросом действие `chart/data` исполняет запрос со сдвигом времени и показывает оба, GET называет только основной. Слой аннотаций — тоже запрос, которого GET не называет: не мерился, исключён по построению |

Legacy-viz на корпусах:

- 4.1.2: `area`, `bubble`, `chord`, `country_map`, 7 `deck_*`, `dist_bar`, `horizon`, `line`,
  `mapbox`, `para`, `world_map`;
- 6.1: `bubble`, `chord`, `country_map`, `horizon`, `para`, `world_map`. Deck.gl, `line` и
  `dist_bar` здесь идут через `/api/v1/chart/data`.

Инвентарю нужен список по версии из исходников Superset, а не из корпуса.

Правило выведено на тех же корпусах; отложенной выборки нет. Механизм каждой проверки показан
пробой или закреплён мутантом: [`stand/area_mutants.py`](stand/area_mutants.py) меняет в записи
чарта из области одну вещь — ту, что видит инвентарь, — и требует, чтобы нужная проверка его
отсекла. 13 мутантов на чартах 125 и 133 (4.1.2), 108 и 116 (6.1) — все отсечены. Правило до
ревью r1 пропускало 7 из 13: дефолт фильтра времени, первое значение, фильтр по вкладке, фильтр
с пустым `chartsInScope` и дефолтом без `extraFormData.filters`, ключ, удалённый из `params`,
смена датасета, датасет вне ответа. Пустой `chartsInScope` — форма фильтра пробы: первая
переработка после ревью доверяла этому списку, и чарты пробы (153, 154 / 136, 137) проходили
`plain`; из области их отсекал только `saved`. Мутант закрепляет исправление. Мутанты
синтетические: это ответы, какие дал бы Superset, а не прогон стенда. Три из них — дефолт
фильтра времени, удалённый ключ и смена датасета — после ревью r2 повторены живьём на 4.1.2
(раздел «Пробы»).

Отсутствие пропущенных чтений у `query_context` автозаписи — наблюдение, не следствие правила: у
203 чартов финальных прогонов, которые не проходят одну проверку `saved`, SQL GET расходится с
дашбордом у 28 и не пропускает ни одного чтения. Значение по умолчанию контрола, которое
добавляет колонку, на корпусах не встретилось. Чартов в области мало, потому что стенд сохранял
из UI только чарты C2: у примеров владелец не `admin`, и «Перезаписать» ему недоступно
(`results/41-c1v.json`).

## Метод

`measure.py` на каждый дашборд записывает три GET инвентаря и `chart/{id}` как есть, затем
`GET chart/{id}/data?type=query` каждого чарта с журналом движка за окно этого GET. Потом
дашборд открывается в headless Chrome под нужным пользователем: клик по каждой вкладке,
прокрутка. Каждый запрос данных (`/api/v1/chart/data` или `/superset/explore_json/`)
записывается с телом и ответом, журнал движка — один на всё открытие дашборда.

- **Нормализация.** Пробелы схлопываются, хвостовые `;` и `FORMAT` снимаются только вне
  литералов в кавычках и строчных комментариев; комментарий `--` сохраняет свой перевод строки
  (ревью r2). Побайтно GET и дашборд не совпали ни разу: «равен» в таблицах — после
  этой нормализации.
- **Без учёта дат.** Второе сравнение не различает литералы дат: относительный диапазон
  отрисовывается в момент запроса. Пары, равные только так (5 чартов C1 на 4.1.2, 10 на 6.1,
  на C2 — ни одной), в `results/` с `time_range`; в каждой различаются только литералы
  момента прогона.
- **Дашборд и движок.** SQL, который показал дашборд, ищется в журнале движка за окно открытия
  дашборда — одно на дашборд, не на запрос — как целый statement после нормализации; на 6.1 —
  после раунд-трипа sqlglot.
- **Чтения.** Набор чтений — имена колонок, на которые ссылается SQL (sqlglot), без ссылок на
  собственные алиасы `SELECT` в `ORDER BY` и `GROUP BY`. Пропущенное чтение — колонка SQL
  дашборда, которой нет в GET; лишнее — наоборот. Имена без таблицы: колонки с одним именем из
  разных таблиц не различаются.
- **GET не исполняет запрос плитки** ни в одном прогоне. В окне GET Jinja-чарта на 6.1
  открывается соединение с ClickHouse (`SELECT version(), timezone()`, `system.settings`,
  `SELECT 1`), но запроса плитки нет. В одном окне 4.1.2 (чарт примеров 70 на PostgreSQL)
  журнал ClickHouse показал запросы метаданных `dm.sales_wide` — тоже не запрос плитки.

## Без `query_context`

Чарту без `query_context` GET отвечает 400 «Chart has no query context saved»: 109 из 110 чартов
C1 на 4.1.2 и 102 из 102 на 6.1. У чартов C2 при первом открытии в Explore `query_context` не
было ни у одного из 44 на каждой версии.

Открытие чарта в Explore пишет `query_context` само: фронт шлёт `PUT /api/v1/chart/{id}` с
`query_context` и `query_context_generation: true`. Для такой записи сервер не проверяет
владельца (`is_query_context_update` в `superset/commands/chart/update.py`, тот же код в 6.1).
`inventory_reader` получил PUT 200 на каждый чарт C2, который открыл: 43 на 4.1.2 и 42 на 6.1. На
4.1.2 `heatmap_v2` Explore не записал никому; на 6.1 два чарта проб записал `admin`. Инвентарь так
не делает: это запись.

| | 4.1.2 | 6.1 |
|---|---:|---:|
| C1: чартов с `query_context` после открытия в Explore | 110 из 110 | 100 из 102 |
| C1: GET 200 | 108 | 100 |
| C1: GET не ответил | `deck_arc`, `deck_path`: 400 «Empty query?» | `word_cloud`, `echarts_area`: Explore не записал `query_context` |

## Числа

Финальные прогоны (`*-c1w`, `*-c2w`) — после открытия в Explore, проб и сохранений, на образах с
ожиданием блокировки SQLite (раздел «Шум стенда»). «Равен» — после нормализации (раздел «Метод»);
строки области — без учёта дат; «не измерено» — дашборд не показал SQL плитки. Чтения не
измерены, когда одна из сторон не разбирается sqlglot или её нет.

  отвечает 400. На 6.1 C2 — `line` и `dist_bar`, сломанные сохранением.
- **SQL дашборда не найден целиком.** На 6.1 C2 `time_compare` показывает основной запрос и
  запрос со сдвигом одной строкой через `;`, движок исполняет их по отдельности.
- **Где GET расходится.**
  - C1, 4.1.2: legacy-viz (20 чартов); pie ×9 без `ORDER BY`; table ×2; `pivot_table_v2`,
    `tree_chart`, `bubble_v2`; GET 400 у двух `deck_*`.
  - C1, 6.1: pie ×8 без `ORDER BY`; `box_plot` ×2 и `deck_polygon` с другим `LIMIT`;
    `bubble_v2` ×2, `tree_chart` и table ×2; legacy `chord`, `country_map`, `horizon`,
    `world_map` ×3; GET 400 у двух.
  - У legacy-viz GET и пропускает чтения: дашборд читает колонку, которой GET не называет
    (`country_code` у `world_map`, `country_name` и `city` у `bubble`, `lat`/`lon` у `mapbox`
    и `deck_*`, `dept_id` у `country_map`, `order_date` и `date` у `horizon`). Без `api` чтения
    пропускает только `query_context`, не согласованный с `params` (`fresh`): `pivot_table_v2`
    C1 (`ds`) и проба stale (`category`).
  - C2: legacy-viz, нативный фильтр, stale, `time_compare`, на 6.1 ещё `waterfall` (автозапись
    с другим `LIMIT`). Все — вне области.

## Superset 6.1

**Форма ответа.** Сравнение ключей трёх GET инвентаря, `chart/{id}` и GET type=query на
нетронутом C1 (`shape_diff.py rec/41-c1 rec/61-c1`):

- в 6.1 добавлены `uuid` и `datasource_*` у чарта; `native_filter_configuration`,
  `chart_configuration`, `global_chart_configuration` в `json_metadata` дашбордов примеров;
  `uuid` у колонок и метрик датасета; `currency_code_column`; десятки ключей `form_data`
  (`matrixify_*`, `bar_stacked`, `border_color` и другие);
- в 6.1 нет `params` и `currency_formats` у датасетов; инвентарь их не читает.

**Читатель v1** (`inventory_forms.py`, код инвентаря `ad6d538`):

| | 4.1.2 | 6.1 |
|---|---|---|
| C1, до проб | 11 дашбордов: 9 записаны, 2 отказаны (12 чартов; `UNION`, который не разбирает guard); 6 чартов типизированы | 9 дашбордов: 7 записаны, 2 отказаны (12 чартов); 2 чарта типизированы |
| C2, после проб | 10 дашбордов: 8 записаны, 2 отказаны (Jinja в SQL датасета; датасет без схемы); 6 типизированы | то же: 8 и 2; 4 типизированы |

На 6.1 чарт типизируется реже по трём причинам:

- нативные фильтры в примерах: другой корпус C1, а не другой читатель;
- ключи `form_data` вне белого списка: `limit` — на обеих версиях (5 причин отказа типизации на
  C1 4.1.2, 8 на 6.1), `bar_stacked` — только на 6.1;
- сохранение из UI 6.1 пишет новые ключи (`matrixify_*` у pie, `border_color` у `heatmap_v2`),
  и эти чарты C2 становятся SQL. Это подтверждено на C2, корпус которого на обеих версиях
  один.

Неизвестный ключ оставляет завышенное чтение, как задумано, — ошибок формы нет.

## Шум стенда и повторы

- **SQLite.** Метаданные Superset — SQLite образа. Дашборд с дюжиной чартов читает её, пока журнал
  событий пишет, и 5 с ожидания блокировки не хватало: 500 «database is locked». Скрипты повторяют
  такой GET. Финальные прогоны `41-c1w`, `41-c2w`, `61-c1w`, `61-c2w` сняты на образах с
  ожиданием 30 с. Ранние прогоны 6.1 (`61-c2`, `61-c2v`) — без него, и часть плиток там не
  измерена.
- **Вход в 6.1.** Страница входа 6.1 пишет журнал событий, пока отправляется форма, и ответ без
  сессии иногда заменяет куки новой сессии. Вход проверяется через `/api/v1/me/` и
  повторяется.
- **Explore 6.1.** Страница иногда открывается с «Missing dataset», и «Сохранить» недоступно.
  Первая проба сохранения (`61-c2v`): 4 из 8 чартов так и не сохранились, один не дождался PUT;
  повтор (`61-c2v2`) сохранил все 5.
- **Stale на 4.1.2.** `results/41-c2.json` несёт первую попытку без CSRF-токена (PUT 400); проба —
  `41-c2stale`.
- **Проба REST.** В первом запуске `run_rest.sh` шаг замера упал: в оболочке `nohup` не было
  `docker` в `PATH`. Сохранения прошли; замер повторён отдельно, в опубликованный скрипт
  добавлен `PATH`.

## Не сделано

- Слои аннотаций не мерились: исключены из области по построению (`single`).
- Первое значение нативного фильтра при загрузке и фильтр по вкладке живьём не мерились:
  правило отсекает их по построению, это проверяют мутанты.
- Дефолт фильтра времени, удалённый ключ, смена датасета и REST-сохранение после автозаписи
  мерились только на 4.1.2.
- Superset 5.x не мерился: только pin 4.1.2 и 6.1.0.
- Импорт дашборда не мерился, и исход неизвестен в обе стороны. Если импорт ставит
  `last_saved_at`, импортированный чарт может попасть в область с `query_context` источника — в
  том числе записанным автозаписью Explore; если не ставит — чарт вне области.
- Чтения сравниваются по именам колонок: одинаковые имена из разных таблиц не различаются. У
  чарта 139 после смены датасета имена те же, а источник другой — его отсекает `fresh`, не
  сравнение чтений.
- Список legacy-viz взят из корпусов; полный список по версии — из исходников, в E4b.
- Отложенной выборки нет: правило проверено на тех же корпусах, на которых выведено.

## Воспроизведение и файлы

- [`stand/`](stand/) — стенд и скрипты замера. Корень стенда — `$E4A_STAND` (по умолчанию
  `~/e4astand`), секреты — в его `.env`. Два venv:
  - `pwvenv` — Python с Playwright и httpx: `measure.py`, `stale.py`, `tc_probe.py`,
    `rest_save.py`, `live_probe.py`;
  - venv проекта с чекаутом `ad6d538` (`uv sync`, sqlglot оттуда): `c2_setup.py`,
    `inventory_forms.py`, `analyze.py`, `area.py`, `area_mutants.py`, `summarize.py`.
- Порядок:
  1. `stand_up.sh 41`, замер C1 как загружен;
  2. открытие C1 в Explore, замер;
  3. `c2_setup.py 41`; зритель и его роль — `reader_role.py` в контейнере `e4a_superset41`, затем
     `E4A_READER_ROLE_ID=<id> c2_setup.py 41` заводит правило RLS (на 6.1 то же делает
     `run_61.sh`); `c2_run.sh 41`, `stale.py`, сохранение из UI (`measure.py --ui-save`);
  4. то же на 6.1: `run_61.sh`, `run_61b.sh`, `run_tc.sh 61` (с `run_61c.sh`);
  5. `run_41w.sh` и `run_61d.sh` — финальные прогоны;
  6. `run_forms.sh`;
  7. после ревью r1: `run_rest.sh` (проба REST на 4.1.2); мутанты —
     `area_mutants.py rec/41-c2w/dashboard_12.json 125`, так же 133 (`dashboard_13`), 108 и
     116 на `61-c2w`;
  8. после ревью r2: `run_live.sh` — живые пробы на 4.1.2 после финальных прогонов (меняют
     дашборд 12 и чарты 139, 145).
- `run_41w.sh` и `run_61d.sh` печатают область с `--rls <датасет stores>`, то есть исключают и
  чарт RLS. Опубликованные сводки — без флага: `summarize.py results rec/<прогон> …` по всем
  прогонам из `results/`.
- Копии отличаются от запущенных путями к стенду и форматированием (ruff, black). `analyze.py`,
  `area.py` и `summarize.py` — версии после ревью r1 и r2: правило области, нормализация и
  чтения изменены, и сводки пересчитаны ими по тем же сырым записям.
- [`results/`](results/) — `summarize.py` по каждому прогону:
  - счётчики и строки сравнения по чартам;
  - строки правила области (для прогонов со списком чартов);
  - пары SQL GET и дашборда у расходящихся чартов;
  - итоги проб без тел запросов.

  Сырые записи (ответы, журналы движка) остались на стенде.
