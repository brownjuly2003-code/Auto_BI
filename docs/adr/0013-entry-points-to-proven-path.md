# ADR 0013: от точек входа к пройденному пути — пункты E1–E7

**Статус:** Accepted
**Дата:** 2026-11-14 (черновик), 2026-11-17 (принят)
**Основание:** слово владельца 2026-11-14: «Нужно сделать новый план с учетом»; новая работа
после D6 — по пункту 5 [ADR 0012](0012-post-finish-development.md). Черновик прошёл модельный
аудит Astra xhigh (вердикт «переработать», 21 находка учтена; второго раунда не было). Принят
словом владельца 2026-11-17: «продолжи доработку проекта по новому. Используй в качестве
исполнителя astra 6 xhigh».

## Контекст

Пункты D1–D6 ADR 0012 закоммичены в локальной ветке `decisionops-backlog`. Ничего из D1–D6 не
опубликовано: `main` — версия `0.6.0`. У гейта четыре входа: CLI, комментарий pull request (D3),
MCP (D5), инвентарь Superset (D6). Для плана важно, что на них измерено.

- **Ни один новый вход не пройден на реальной площадке.** Action проверен только offline: на
  GitHub он не запускался. Прогон MCP-сервера с клиентом вне тестов не записан. Инвентарь снят с
  корпуса примеров Superset 4.1.2 и одного дашборда стенда.
- **В бэклоге D3 — граница безопасности Action.** Файл `.env` из checkout'а PR может задать
  переменную подключения, которую не задал workflow, и проба уйдёт на выбранный им хост с
  учётными данными workflow. Версию uv тоже выбирает checkout PR. Незакрытая кавычка в SQL чарта
  кончает `verify` traceback'ом без вердикта. Предупреждения sqlglot печатают SQL из PR в stderr
  ([бэклог](../DECISIONOPS_BACKLOG.md)).
- **Инвентарь редко читает плитку точно.** На корпусе примеров (11 дашбордов, 110 чартов)
  записано 9 дашбордов: типизировано 5 чартов, 60 прочитаны завышенно — `SELECT *` и все
  фрагменты ([спека](../specs/superset-inventory.md)); по всем 110 чартам — 6, 103 и 1 отказ. Такую плитку гейт при любом изменении её
  датасета называет `chart.sql_partial`. Вердикт от этого не меняется: chart impact — evidence, а
  не грейдинг ([спека](../specs/chart-impact-resolution.md)); страдает ответ «какая плитка
  затронута». Вердикт меняет отказ дашборда: `bi.spec_missing` — review. Отказано двум дашбордам
  из 11: 21 и 24 чарта при лимите 12 в `DashboardSpec`; у одного ещё и SQL датасета, который
  ClickHouse не разбирает. Отрисованный SQL корпус не отдаёт: `GET chart/{id}/data?type=query`
  отвечает 400 для 109 чартов из 110.
- **Покрытие dbt — 10 метрик из 54** на фиксированном корпусе артефактов трёх публичных проектов
  dbt-labs. Корпус снят с адаптациями: dbt-core 1.12.6 читает jaffle-shop в обход его
  `require-dbt-version: >=2.0.0`, jaffle-sl-template читается с флагом
  `require_nested_cumulative_type_params: false`
  ([отчёт F4](../reviews/DECISIONOPS_DBT_PUBLIC_2026-11-10.md),
  [отчёт D4](../reviews/DECISIONOPS_DBT_COVERAGE_2026-11-13.md)). Остальные 44 метрики стоят на
  конструкциях вне двух форм формулы (`typed_aggregate`, `typed_ratio`): выражение меры не одной
  колонкой — 23 метрики, время из выражения — 13, фильтр метрики — 9, derived — 7, cumulative —
  5, `fill_nulls_with` — 3, `median`, `percentile`, `sum_boolean`, `join_to_timespine` — по одной.
  Конструкции пересекаются. По записям корпуса снятие гэпа выражения меры даёт до 21 метрики из
  54, вместе с фильтром метрики — до 27, ещё и с временем из выражения — до 36. Оценки верхние:
  за снятым гэпом может открыться следующий, а паритет проверяется последним.
- **Заявленный движок не запускался.** `--dwh greenplum|greengage` принимается, но живьём
  проверены PostgreSQL 16 и ядро 9.4.26; на кластере Greenplum или Greengage гейт не запускался
  ([CURRENT_STATE](../DECISIONOPS_CURRENT_STATE.md), «Что ещё не реализовано»).
- **Рынок.** В срезе 2026-11-13 (контекст ADR 0012) гейта, который доходит в PR до дашборда
  Superset или DataLens, не найдено; после среза поиск не повторялся. Стенд проекта запинен на
  Superset 4.1.2; для проверки инвентаря выбран 6.1 — версия из того же среза.

Вывод: входы построены, но путь «pull request — вердикт — затронутые плитки — проверяемое
evidence» нигде не пройден целиком, а известная граница безопасности Action открыта. Поэтому
план делится на основной путь и расширения. Основной путь: закрыть известные дыры входов,
опубликовать, пройти путь на GitHub с настоящими base и head, сохранить и проверить evidence,
подключить инвентарь входом прогона. Расширения — точность инвентаря, живой Greengage, покрытие
dbt, читаемый отчёт — независимы и основной путь не задерживают. Новая ширина — DataLens, другие
движки — после.

## Решение

1. **Основной путь — E1–E3, в этом порядке.**
   - **E1. Закалка входов — до публикации.** Четыре записи бэклога D3.
     - `.env`: Action не читает `.env` рабочего каталога никогда; у CLI появляется явный режим
       настроек без файла. Тест — на каждую команду, которая читает `Settings`, и на каждую
       переменную подключения.
     - Версия uv, которую ставит Action, не зависит от checkout'а PR.
     - Незакрытая кавычка в SQL чарта — находка guard'а и вердикт вместо traceback.
     - Логгер `sqlglot` заглушён на всём `verify`.

     Готово, когда записи закрыты тестами и мутантами и удалены из бэклога.
   - **E2. Публикация и первые прогоны на площадке.**
     - Публикация. Полный `ci_local`, один pull request ветки `decisionops-backlog` (D1–D6 и E1)
       в `main`, шесть обязательных проверок, слияние — по слову владельца
       ([ADR 0011](0011-public-repository.md)). Версия `0.7.0` в `pyproject` и CHANGELOG, без
       тега. Верх README — о гейте: что он проверяет, его входы, быстрый прогон пилота; v1 — ниже.
     - Демонстрация. В репозитории появляются каталог примера с базовой семантикой пилота
       `2026-08-25-ch-tz-margin` и workflow, который зовёт Action по SHA коммита `main`, без
       `dwh` и без секретов. Затем демонстрационный pull request в этом же репозитории; он не
       сливается. В нём два прогона: коммит без изменения семантики, затем коммит с изменением
       пилота.
     - Путь считается пройденным, когда выполнено всё:
       1. base читается из checkout'а `pull_request.base.sha`, candidate — из головы PR;
          каталоги, подготовленные заранее, не годятся;
       2. прогон без изменения семантики даёт вердикт, записанный заранее по локальному прогону
          на тех же входах; прогон с изменением — `block`, как в пилоте;
       3. комментарий один: после второго коммита он обновлён, а не добавлен;
       4. в записи разведены вердикт, код выхода гейта и статус шага при выбранном `fail-on`;
          комментарий без вердикта путь не закрывает;
       5. bundle каждого прогона сохранён артефактом workflow, при `block` тоже; скачанный bundle
          проверен `decision evidence`, его digest равен digest'у в комментарии; срок хранения
          артефакта записан, а bundle прогона с `block` положен в репозиторий рядом с записью
          демонстрации;
       6. независимость версии uv от checkout'а PR проверена вживую — либо записана как
          непроверенная, с причиной.
     - MCP. Сессия сервера с клиентом вне тестов: вызваны все инструменты на пилоте, ответы
       сверены с CLI; клиент и его версия записаны.
     - Дефекты первых прогонов. Неверный вердикт и граница безопасности чинятся до закрытия E2;
       остальное — в бэклог.
   - **E3. Инвентарь как вход прогона PR.**
     - Job pull request не получает учётных данных Superset. Инвентарь снимается вне его —
       оператором или доверенным workflow ветки по умолчанию: ручной запуск, код инвентаря
       закреплён по SHA, учётная запись Superset только читает названные дашборды. Результат
       хранится снимком: каталог спек и `inventory.json` в репозитории. Прогон PR читает снимок
       входом `dashboards`. Запрет `pull_request_target` остаётся.
     - Последовательность входов описана в спеке инвентаря и покрыта offline-тестом от ответов
       Superset до комментария. Сопоставление refs и идентификаторов Superset хранится в
       репозитории; ref из `delivery.dashboards` без спеки виден как `bi.spec_missing`. Снимок
       снимается против модели ветки по умолчанию. Exit 0 — снимок полный; 3 — отказанные
       дашборды названы, и гейт ответит на них `bi.spec_missing`; 2 — снимка нет, прежний
       остаётся. Снимок может отставать от BI: свежесть — дело того, кто снимает, а не вердикт,
       и спека это говорит.
     - Демонстрация. Каталог примера получает снимок, снятый инвентарём со стенда, и
       демонстрационный PR проходит на нём ещё раз.

     Основной путь закрыт, когда записан E3: путь от pull request до вердикта, затронутых плиток
     и проверяемого evidence пройден на GitHub.
2. **Расширения — E4–E7.** Они не зависят друг от друга. Порядок рекомендуемый; владелец может
   переставить или снять любое.
   - **E4. Точность инвентаря Superset.**
     - **E4a. Исследование.** Стенд Superset 6.1 рядом с запиненным 4.1.2; пишущий адаптер v1 и
       его pin не меняются. Закрепляются корпус и знаменатели: корпус примеров целиком на обеих
       версиях — с чартами без `query_context` и с отказами — и свой корпус на ClickHouse, по
       чарту на viz над демо-DM. Вопросы: какие чарты и при каких условиях отдают отрисованный
       SQL; от чего он зависит — пользователь, RLS, Jinja, время, фильтры дашборда, несколько
       запросов одного чарта, диалект базы датасета; называет ли Superset схему по умолчанию
       подключения; какие версии Superset читает инвентарь и что в форме ответа 6.1 другое.
       Эталон чтений не зависит от читателя гейта: запрос, который движок действительно исполнил
       (журнал запросов ClickHouse). Выход — воспроизводимые числа и запись решения: в какой
       области отрисованный SQL даёт право назвать плитку прочитанной целиком. Вне этой области
       остаётся именованный гэп. Версии Superset и версии читателя сравниваются отдельно.
     - **E4b. Реализация — по решению E4a.** Уровни чтения: типизированный (D6) — отрисованный
       SQL в разрешённой области — составной SQL по viz из белого списка ключей `form_data` —
       завышенное чтение. Неизвестный ключ оставляет завышенное чтение. Датасет без схемы
       остаётся отказом; схема подставляется, только если её для этого подключения назвал сам
       Superset. Нативные фильтры дашборда и дашборд больше 12 чартов — по решению владельца
       (п. 6); без него гэп и отказ остаются. SQL датасета, который ClickHouse не разбирает,
       остаётся отказом: цель «11 из 11» не ставится.

     Мера — на закреплённом корпусе, до и после: записанные и отказанные дашборды по причинам;
     типизированные плитки — только они могут быть `computes_metric`; плитки, прочитанные
     целиком; пропущенные и лишние чтения против эталона. Пропущенное чтение — ложное «плитка не
     затронута», допустимое число — ноль. Это снижение неопределённости impact, а не другой
     вердикт: `chart.metric_unread` у SQL-плитки, которая читает колонки метрики, остаётся.
   - **E5. Живой Greengage.** Greengage 6 одним узлом с сегментами на Mac; Greengage 7 — тем же
     прогоном, если стенд помещается в память. Живые сценарии `--dwh`: имена типов (D1),
     отношения и отказы (D2), доступ роли — и то, чего нет в ядре 9.4.26: append-optimized и
     колоночные таблицы, внешние таблицы, партиции, план с motion-узлами. Расхождение с ядром
     исправляется или записывается с причиной. Условия запуска: сборка из исходников Greengage
     закреплённой ревизии; сторонний образ — только по слову владельца и с закреплённым digest,
     его происхождение записывается как непроверенное. В VM стенда нет рабочих секретов и
     рабочих данных, каталоги хоста не смонтированы, сеть нужна только сборке; после проверки
     стенд удаляется. Предел: сборка и подготовка — не дольше одного рабочего дня, подъём
     кластера — две попытки. Не уложились — запись о невоспроизводимости на этом стенде, а
     документы называют `greenplum|greengage` проверенным на ядре 9.4.26, не на кластере.
   - **E6. Покрытие dbt.**
     - Корпус и мера. Знаменатель 54 — фиксированный корпус артефактов с адаптациями F4; он
       держит регрессии, а не доказывает применимость к чужим проектам. Мера считается только
       после того, как сохранённые артефакты заново разрешены текущим кодом, и тремя числами:
       метрики без гэпов конструкций; из них совместимые с контрактом на своей таблице; из них с
       доказанным паритетом. Каждый новый класс выражений получает свои случаи вне корпуса:
       NULL, типы, границы времени. Артефакты jaffle-проектов в репозиторий по-прежнему не
       кладутся: лицензии у них нет.
     - **E6a. Обзор и классы паритета.** Какие выражения стоят за 23 метриками с выражением меры
       — по сохранённым артефактам F4. Классы паритета и правило точности доли читают тип по
       имени, которое печатает движок (запись D1 бэклога): уходит ложная advisory-находка
       `sql.ratio_inexact_term` на `BIGINT` ClickHouse.
     - **E6b. Выражение меры.** Формы по обзору — только те, что документация MetricFlow
       описывает как конструкцию, — с паритетом PostgreSQL и ClickHouse.
     - **E6c. Фильтр метрики.**
     - **E6d. Время из выражения — после решения владельца (п. 6).**
       [ADR 0008](0008-dbt-semantic-manifest-external-formulas.md) оставляет событийное время и
       grain за native-контрактом и отвечает на время из выражения review
       `gap.external_time_unproven`. Нужны правила для временного выражения, timezone, grain и
       сравнения с контрактом — дополнением ADR 0008. Без решения гэп остаётся.

     Новая форма расширяет контракт формулы: её дизайн — раздел
     [архитектуры](../DECISIONOPS_ARCHITECTURE.md) и ревью дизайна до кода, с перечнем
     потребителей — снимок и diff, impact, reference SQL, pin и closure, паритет. Недоказанное
     сочетание остаётся гэпом.
   - **E7. Отчёт прогона.** Статический HTML: один файл без внешних ресурсов. Строится только из
     bundle, который прошёл `decision evidence`; повреждённый bundle — ошибка, а не отчёт. Новых
     выводов отчёт не делает. Каждое свободное поле — имя, SQL, название из BI, detail —
     выводится экранированным текстом и не читается как HTML или ссылка. Отчёт воспроизводим
     байт в байт, в манифест evidence не входит и несёт версию рендерера. Action прикладывает
     его артефактом.
3. **Чем закрывается срез.** Исследовательский срез (E4a, обзор E6a) закрывается воспроизводимым
   ответом и записью решения о дальнейшем объёме; отрицательный ответ — тоже результат.
   Реализационный срез закрывается перечнем поддержанных случаев, проверками их границ и
   отсутствием регрессий на закреплённом корпусе. Числовой порог реализации назначается после
   измерения базы и записывается до кода. Конструкция dbt или viz Superset, которым точного
   чтения не нашлось, остаются гэпом и строкой бэклога.
4. **Заморозка как в [ADR 0010](0010-finish-line.md) и 0012.** Находки вне E1–E7 идут в бэклог;
   сразу чинится только неверный вердикт по числам. Новое правило: вход не публикуется, пока
   открыта известная запись, по которой файлы pull request получают учётные данные или сетевой
   доступ workflow. Ревью — r1 открытое, r2 закрывающее; что осталось — в бэклог.
5. **Ветка и публикация.** До слияния D1–D6 и E1 работа идёт в `decisionops-backlog`, после — в
   новой локальной ветке от `main`. Push, pull request и слияние — только по слову владельца.
   Обязательная точка публикации — E2; после любого расширения — по слову владельца, с новой
   минорной версией. Теги не ставятся, пакет не публикуется
   ([ADR 0009](0009-local-package-identity-no-publication.md), ADR 0011).
6. **Решения, которые остаются за владельцем.**
   - E2: слово на push, pull request и слияние; каталог примера и демонстрационный PR в этом
     репозитории.
   - E3: живой Superset внутри job pull request в план не входит — только отдельным решением.
   - E4b: граница IR, обе части. Лимит 12 чартов: предложение — оставить его правилом пишущих
     путей и схемы для LLM, а для спеки, прочитанной из BI, снять; до правки перечисляются
     потребители `DashboardSpec`. Нативные фильтры: у фильтра дашборда в IR нет области действия
     по чартам, и impact его не читает; нужны форма и область — либо гэп остаётся.
   - E5: сторонний образ Greengage, если сборка из исходников не удалась.
   - E6: этот ADR разрешает новые формы формулы для выражения меры и фильтра метрики; время из
     выражения — после принятого дополнения ADR 0008; `typed_derived` — только отдельным словом.
   - E6a: новый прогон dbt на публичных проектах, если артефакты F4 не сохранились.
   - Порядок и состав расширений E4–E7.
7. **Срезы идут по одному в одном рабочем дереве.** Offline-гейт и Mac-стенд общие; параллельно
   работают только субагенты внутри среза — ревью, мутанты, документы.
8. **Что план берёт из бэклога.** Остальное остаётся записями бэклога.

## Последствия

- Каждый срез идёт с прежним порядком: мутанты, ревью, полный offline-гейт на Mac, запись в
  журнале статуса, локальный коммит.
- Ревью — по действующему правилу ([CURRENT_STATE](../DECISIONOPS_CURRENT_STATE.md), «Решения»):
  Astra xhigh ([ADR 0006](0006-modelled-review-development-gate.md)); пока у владельца нет
  лимита Codex — независимый Opus-субагент и мутанты. Запись среза называет, кто ревьюил.
- Версии — по правилу [архитектуры](../DECISIONOPS_ARCHITECTURE.md) и по фактическому изменению
  среза. `VERIFIER_VERSION` поднимается, когда гейт способен вынести из тех же входов другой
  вердикт или другой evidence. `CHECK_VERSION` — дополнительно, когда меняется смысл
  существующей проверки; новая проверка двигает только `VERIFIER_VERSION`. Ожидаемо: E1 —
  вердикт вместо падения на незакрытой кавычке; E4b — снятие лимита и новые поля IR меняют ответ
  `bi.contract`; E5 — исправленные расхождения; E6 — новые формы, классы паритета и правило
  точности доли. Новый читатель инвентаря версий гейта не двигает: он меняет входные спеки, а их
  содержимое уже в ключе прогона; версия читателя записывается в `inventory.json`. E2, E3 и E7
  вердиктов не меняют.
- Стенды — только Mac и по одному: Superset 6.1, Greengage и пара PostgreSQL с ClickHouse для
  паритета вместе в память не помещаются.
- После E2 локальная ветка перестаёт быть единственной копией срезов.
