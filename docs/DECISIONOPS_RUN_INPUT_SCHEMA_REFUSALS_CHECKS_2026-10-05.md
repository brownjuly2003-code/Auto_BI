# Run inputs: what a schema refuses of a run input is said in one line — проверки автора

**Дата:** 2026-10-05
**Срез:** T-54; verifier 93 / check 68 — без изменений
**Автор:** Claude Opus 5.5 (`claude-opus-5-5`), напрямую, без MyFlow-исполнителей
**Модельное ревью:** не проводилось

Владелец в этой сессии выбрал прямое исполнение: спеку, код, тесты и доки написал Claude
Opus 5.5, MyFlow не запускался, synthetic Astra xhigh review не было. По
[ADR 0006](adr/0006-modelled-review-development-gate.md) модельное ревью не выполнено, пока
нет фактического результата Astra xhigh, — у этого среза его нет. Всё перечисленное ниже —
проверки автора над собственной работой: не независимое ревью, не human/design-partner
acceptance и не production acceptance. Тесты и пробы прогонялись на Mac (Python 3.13.13,
3.12.13 и 3.14.6; PyYAML 6.0.3, pydantic 2.13.4). Контракт:
[files a command cannot read](specs/unreadable-inputs.md), шестое требование.

Предыдущий срез оставил границу: отказ схемы в одну строку получил только `decision
investigate`. `decision verify` и `decision capture` называли вход прогона, который прочитан
и не принят схемой, и дальше печатали то, что бросил pydantic, так, как он это перечисляет:
строка со счётом ошибок и на каждую ошибку — строка места, строка причины со значением и
строка ссылки на документацию.

На HEAD `4720405` воспроизведено настоящим CLI как процессом над прогоном, который без порчи
проходит, с одной порчей одного файла за прогон. Десять порч: файл заменён списком, текстом,
пустотой, mapping `unknown_key: 1`; дописан один лишний ключ, четыре лишних ключа, ключ с
переводом строки, ключ-число, ключ с одиночным суррогатом; значение не того вида глубоко
внутри документа. Для `decision verify` — каждый из пяти файлов прогона (`model.yaml` base и
candidate, dashboard spec, verified asset, recorded results), для `decision capture` — asset
и `model.yaml` candidate: 70 прогонов.

| Исход | HEAD | Рабочее дерево |
|---|---|---|
| `decision verify`: exit 2, на stderr от 3 до 22 строк | 42 | 0 |
| `decision verify`: exit 2, одна строка | 7 | 49 |
| `decision verify`: exit 4, прогон оценён | 1 | 1 |
| `decision capture`: exit 2, на stderr от 3 до 22 строк | 19 | 0 |
| `decision capture`: exit 2, одна строка | 1 | 20 |

Что стоит за числами HEAD:

- 61 прогон из 70 печатал перечень pydantic. Файл с `unknown_key: 1` на месте verified asset
  — 22 строки (семь ошибок), пустой файл на его месте — 19, четыре лишних ключа в любом
  файле — 13.
- Девять остальных — прогоны, где схему ни о чём не спрашивают: dashboard spec и results,
  которые не mapping (список, текст, пусто — шесть прогонов, `must contain a mapping`), и
  пустой `model.yaml`: у base это модель без таблиц, и прогон оценён (exit 4); у candidate
  `decision verify` отвечает `must contain a mapping`, а `decision capture` идёт к движку
  (в пробе движка нет, и строка — отказ соединения).
- Results file держит результат на каждый asset, а отказ одного из них не говорил, какого:
  `<файл> holds an invalid recorded result: ` и перечень — одинаково под любым ключом файла.

Одиночный суррогат спрошен в процессе на каждой строке и каждом ключе файлов фикстуры, один
и между двумя буквами: 800 документов (по 168 на `model.yaml` base и candidate, по 120 на
metric contract base и candidate, 48 — dashboard spec, 112 — verified asset, 64 — recorded
results), 1200 прогонов двух команд.

| Исход | HEAD | Рабочее дерево |
|---|---|---|
| usage error в 3–7 строк | 642 | 0 |
| usage error в одну строку | 168 | 810 |
| прогон оценён или capture дошёл до движка | 368 | 368 |
| исключение, которое никто не ловит | 22 | 22 |

Теперь вход прогона, который прочитан и не принят схемой, — usage error в одну строку
(`_refusal` в `auto_bi/decision/use_cases.py`, `schema_reason` в `auto_bi/yaml_document.py`).

- Слова, которые называют файл, прежние: `<файл> is not a valid semantic model: `, `<файл> is
  not a valid DashboardSpec: `, `<файл> is not a valid verified asset: `. После них — отказы
  схемы, как у входов `decision investigate`: `<место>: <причина>` для первых трёх ошибок
  через `; `, затем `; (+<n> more)`; без значения и без ссылки, каждая серия пробельных
  символов — один пробел.
- Recorded result назван ключом, под которым его держит файл: `<файл> holds an invalid
  recorded result for <ключ>: <отказы>`. Ключ записан так, как Python пишет его литерал:
  текст в кавычках, перевод строки и одиночный суррогат внутри — escape-последовательностью,
  число, пустота и булево — как их построил PyYAML. К моменту чтения файла ничто не требует,
  чтобы ключ был id asset'а, а строка остаётся одной, каким бы ключ ни был. Места отказов —
  места внутри этого результата: `result.rows.1`, `attestation.origin`, `<root>` для
  значения, которое вообще не результат. Результаты читаются в порядке файла, первый
  отвергнутый кончает чтение.
- Отказ схемы модели сказан о `model.yaml`. Отказ любой другой схемы, брошенный, пока граф
  ref строится из файлов, принятых своими схемами, сказан о ref с именем этой схемы: `cannot
  load semantic ref <ref>: not a valid <схема>: <отказы>` — места тогда принадлежат тому,
  что описывает эта схема, а не файлу ref. Раньше схему называла первая строка перечня
  (`1 validation error for SemanticGap`).
- `ValueError`, который не отказ схемы, — для ref, для `model.yaml` candidate, прочитанного
  второй раз под компиляцию, для dashboard spec, для assets и для recorded result — сказан
  своим текстом, где каждая пробельная серия — один пробел, или своим классом, когда текста
  нет.
- `VerifiedAssetRepository.load` бросает `VerifiedAssetFileError` с этой одной строкой, а
  `ValidationError` схемы остаётся его причиной: кто загружает репозиторий в программе,
  по-прежнему получает каждый отказ со значением.
- В каждом случае exit 2, `error: ` и одна строка на stderr, пустой stdout; evidence-каталог
  не создан, запрос не открыт, output не записан.

Версии evidence не менялись: `VERIFIER_VERSION` 93, `CHECK_VERSION` 68. Ни один вход,
дававший bundle или captured result, не даёт другого; меняется только текст usage error,
которые и прежде были usage error.

Выбор. Границу назвал срез T-53; срез выбрал оркестратор, Astra-выбора по ADR 0006 для него
нет. Решения внутри среза — тоже автора:

- Формат отказа схемы — тот же `schema_reason`, что у `decision investigate`: одна
  функция на все команды, которые печатают отказ схемы строкой usage error.
- Слова, называющие файл, не тронуты: их закрепляют тесты предыдущих срезов, и по ним
  оператор уже отличает «не прочитан» от «прочитан и не принят».
- Ключ recorded result печатается через `repr`, а не как текст: ключ YAML может быть числом,
  пустотой или булевым, может держать перевод строки или одиночный суррогат; литерал
  остаётся одной строкой, которую примет любой поток, и отличает `1` от `'1'`.
- Первый отвергнутый результат кончает чтение — как первый отвергнутый вход кончает
  `decision investigate`: строка usage error одна, и она об одном файле и одном месте.
- Отказ чужой схемы сказан о ref, а не о `model.yaml` (решение T-50), но теперь с именем
  схемы: без него места отказа (`reason`, `path`) читались бы как места файла.
- `ValueError` без текста назван классом: пустая строка после двоеточия ничего не говорит.
- Что `decision capture` печатает после `cannot capture <asset id>: `, не тронуто: это слова
  движка или схемы аттестации о том, что получено уже после чтения входов (см. границы).

  требования и пять границ приведены в соответствие.
- Новый модуль `tests/test_run_input_schema_refusals.py` — 75 тестов в 23 функциях. Он не

Границы. Срез закрывает файлы, которые прогону передают. То, что `decision capture` печатает
после `cannot capture <asset id>: `, — текст брошенного как есть. Проба в процессе с
запросом, который отвечает: `--captured-at`, который не RFC 3339 UTC timestamp (слово,
смещение вместо `Z`, без зоны, пробелы, перевод строки после timestamp), кончается exit 2 с
четырьмя строками перечня pydantic для `ResultAttestation` — и только после того, как запрос
исполнен; `--environment` из пробелов, из двух строк или с одиночным суррогатом
аттестуется как передан, и файл записывается. Одиночный суррогат как значение входа прогона
закрыт только там, где его отвергает схема: в 22 прогонах из 1200 `decision verify`
по-прежнему кончается исключением, которое никто не ловит. Схема приняла значение, а у
digest прогона для него нет формы — `CanonicalizationError`: заголовок дашборда, id и
заголовок чарта (6 документов spec из 48), окружение и исполнитель аттестации (4 документа
results из 64); либо сравнение результатов не может его процитировать — `ValidationError`
для `ResultDifference`: `unit` колонки и текстовое значение ячейки, в ожидаемом результате
asset'а (6 документов из 112) и в recorded result (6 из 64). Ещё в 368 прогонах значение
принято: прогон оценён или capture дошёл до движка. Пустой `model.yaml` читается тремя
способами, как прежде (см. выше). Ключ recorded result при чтении файла не проверяется:
результат под ключом с одиночным суррогатом на месте id asset'а прочитан, и прогон оценён.
Причины отказов — предложения pydantic установленной версии (2.13.4), другая версия может
сказать иначе; ключ файла прогона с одиночным суррогатом pydantic отвергает без места —
`<root>: Input should be a valid string, unable to parse raw data as a unicode string`.
«Одна строка» значит «без перевода строки»: сжимаются только пробельные серии, любой другой
символ ключа или процитированного значения печатается как есть. Строка usage error может
цитировать файл: ключ документа как место отказа, ключ recorded result, значение в причине
validator'а; она печатается в stderr и не запечатывается. Windows: тесты там не
запускались. BI и DWH не запускались: проверка offline. Независимого ревью у среза нет — ни
модельного, ни человеческого.
